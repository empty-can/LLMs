## 1. auto モードが既定の開始モードになった

権限モードのページに **セッションがどのモードで始まるか** という節が新設されました。ターミナルで新しいセッションを始めたときのモードは、当てはまる最初の段で決まります。①`--permission-mode` フラグまたは `--dangerously-skip-permissions`、②設定ファイルの `permissions.defaultMode`、③組み込み既定、の 3 段です。`.claude/settings.json` と `.claude/settings.local.json` の `"auto"` は効かず、その場合 Claude Code は `~/.claude/settings.json` の `defaultMode` を使わずに組み込み既定へ落ちます。それ以外の値はどの設定ファイルからでも適用されます。再開したセッションは、上記のフラグを渡さない限り元のモードを保ちます。

組み込み既定は 6 行の表になり、最初に当てはまった行が勝ちます。Manual（`default`）で始まるのは、いずれかの設定ファイルが `disableAutoMode` を `"disable"` にしている場合、フィーチャーフラグの取得がオフの場合とインストール・アップグレード直後の最初のセッション、`claude -p` と Agent SDK、Amazon Bedrock・Google Cloud's Agent Platform・Microsoft Foundry・Claude Platform on AWS・サインイン済みの Claude apps gateway セッション、そして Enterprise プランまたは Claude Console の API キーです。`auto` で始まるのは、Pro・Max・Team プランでターミナルまたは VS Code 拡張から使う場合です。組み込み既定の `auto` には macOS・Linux・WSL で v2.1.228 以降、ネイティブ Windows で v2.1.233 以降が必要で、それより前のバージョンは Manual で始まります。3 段のいずれかが `auto` を選んでも、そのセッションで auto モードが使えない場合は Manual で開始します。組み込み既定が初めてセッションを auto モードで開始したときは案内が出ます。ターミナルではセッション冒頭に 1 度、VS Code 拡張では新規会話画面のカードとして、閉じるまで残ります。Pro・Max・Team プランで `~/.claude/settings.json` が別の `defaultMode` を設定していて他の設定ファイルが何も設定していない場合、ターミナルのセッションはその設定のまま始まり、Claude Code が 1 度だけ auto モードに変えるかどうかを尋ねます。断れば設定はそのまま残ります。

**別の権限モードで開始する** という小節も新設され、開始モードを決める 4 つのスコープが表にまとまりました。これから始める 1 セッションはフラグで、このマシンの全ターミナルセッションは `~/.claude/settings.json` の `permissions.defaultMode` で、1 つのプロジェクトはそのプロジェクトの `.claude/settings.json` で、組織全体は管理設定で指定します（auto モードを選べなくするには `permissions.disableAutoMode` を使います）。VS Code 拡張自身の解決順も 4 段の一覧として明示されました。①`claudeCode.initialPermissionMode`、②直近にモード指示器で選んだモード（Manual・Edit automatically・Auto のみ。Plan と Bypass permissions はその会話限り）、③Pro・Max・Team プランでフィーチャーフラグが取得できる場合の管理設定または `~/.claude/settings.json` の `permissions.defaultMode`、④組み込み既定、の順です。拡張は開始モードのためにプロジェクト設定を読むことはなく、`claudeCode.claudeProcessWrapper` が設定されている場合は③④も適用されません。`disableAutoMode` の効果も変わり、`--permission-mode auto` で起動したセッションは起動時に拒否されるのではなく Manual で始まるようになりました。

この切り替えはドキュメント全体の言い回しに波及しています。`Shift+Tab` は `auto` からだとまず `default` に切り替わり、そこから従来のサイクルを回ります。「既定の権限モードでは」と書かれていた箇所は「Manual モードでは」に置き換わり、ツールリファレンス・権限・サンドボックス・プロンプトキャッシュ・ターミナル設定・対話モード・JetBrains・デスクトップと Web のクイックスタート・チャネルリファレンスの手順・Agent SDK の権限ページなどが対象になりました。セッションのページには再開時に権限モードをどう復元するかの規則が加わり、環境変数のフィーチャーフラグ関連の一覧は auto モードに関する 2 項目から始まる形に書き換えられています。

## 2. Claude が名付けたサブエージェントがチームメイトとして起動する

サブエージェントのページに **サブエージェントの名前** という節が新設されました。Claude は Agent ツールの呼び出しに `name` パラメータを渡してサブエージェントに名前を付けることができ、事前に確認せず自分の判断で付けることもあります。名前が付くとそのサブエージェントは宛先として指定できるようになり、終了後に名前でメッセージを送ったり再開したりできます。エージェントチームが有効な対話セッションでは、メイン会話から `name` 付きで起動したサブエージェントは代わりに**チームメイトとして起動します**。例外はフォークの場合と、呼び出し自体に `isolation` を渡した場合だけで、サブエージェントのフロントマターに書いた `isolation` では防げず、その場合チームメイトはメインセッションの作業ディレクトリで動きます。

エージェントチームのページも合わせて書き換わりました。**Claude がエージェントチームを始める方法** はこれまで「あなたが依頼する」「Claude が提案してあなたが承認する」の 2 つの経路を挙げ、いずれの場合も主導権はあなたにあり、Claude は承認なしにチームメイトを起動しない、と結んでいました。今回からは、エージェントチームが有効な間に Claude が `name` 付きで Agent ツールを呼べばチームメイトが起動し、Claude Code は確認を求めない、と書かれています。Claude は後でメッセージを送れるように通常のサブエージェントにも自分で名前を付けるため、依頼していなくてもチームが形成されうる、とも明記されました。チームメイトの起動には対話セッションが必要で、`-p` の非対話モードと Agent SDK セッションでは、エージェントチームが有効でも名前付きサブエージェントは通常のサブエージェントとして動きます。

新設のトラブルシューティング **Claude がサブエージェントではなくチームメイトを起動する** が、その帰結を扱います。サブエージェントは完了時に結果が Claude に返るのに対し、チームメイトは待機通知が「停止した」ことを伝えるだけで出力を運ばないため、サブエージェントの結果を待つオーケストレーションは止まりうる、というものです。サブエージェントに戻すには `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` を `0` にします。新しいセッションを始める必要はなく、設定ファイルの `env` は保存時に実行中のセッションへ再適用され、変数はサブエージェントを起動するたびに読み直されるためです。ユーザーの `settings.json` の `0` はシェルの export を上書きしますが、プロジェクト設定・ローカル設定・`--settings` のペイロードは後から適用されるため、そこで `1` にされれば勝ちます。管理設定は全てのソースの後に適用されるので、組織が有効にしている場合は管理者に依頼することになります。設定変更後も Claude はサブエージェントに名前を付けることがあり、その名前は `SendMessage` の宛先として引き続き機能します。待機通知がチームメイトの出力を運ばないことは、コンテキストと通信の節にも明記されました（結果を共有するにはリードにメッセージを送るか共有タスクリストを更新する必要があります）。

- [Create custom subagents - Claude Code Docs (English)](https://code.claude.com/docs/en/sub-agents#subagent-names)
- [Orchestrate teams of Claude Code sessions - Claude Code Docs (English)](https://code.claude.com/docs/en/agent-teams#claude-spawns-teammates-instead-of-subagents)

## 3. `/goal` の評価が 3 値になった

`/goal` の評価器はこれまで「はい」か「いいえ」を返していましたが、今回から短い理由とともに 3 つの判定のいずれかを返すようになりました。**未達成** なら Claude は作業を続け、理由を次のターンの指針として受け取ります。**達成** なら Claude Code はゴールをクリアしてトランスクリプトに達成エントリを記録します。**達成不可能** は評価器がその条件は決して満たされないと判断した場合で、Claude Code はゴールをクリアし、理由とともに失敗エントリを記録するため、自分でクリアする必要はありません。ページの 1 行説明も「条件が満たされるか、達成不可能と判断されるまで」に変わり、これが今回 `llms.txt` で変わった唯一の行です。

もう 2 つの挙動が文書化されました。1 つは停滞の検出で、Claude が進捗を出さないまま評価器に答え続けると（数ターン連続でツールを使わない状態）、Claude Code はループを止め、警告を出し、ゴールを設定したまま制御を返します。評価は次のプロンプトから再開します。もう 1 つは、ターンが終わった時点でサブエージェントやバックグラウンドのシェルコマンドがまだ動いている場合、そのターンの評価をスキップし、次のターンの終了時に評価するというものです。トランスクリプトの表示も変わり、最新の理由だけでなく評価器が返した判定が毎回表示され、Ctrl+O でその理由を見られます。`/goal clear` の説明は「条件が満たされる前に」から「解決する前に」になり、権限に関する記述も新しい開始モードに合わせて、ゴールのターンを無人で回すなら auto モードで `/goal` を実行し、Manual モードでは設定が許可していないツール呼び出しの前に Claude が確認する、と書き直されました。

`/goal` はセッションスコープのプロンプトベース Stop フックのラッパーなので、フックのページにも同じ変更が入っています。プロンプトフックのレスポンススキーマに省略可能な `impossible` フィールドが加わり、条件が決して満たされないとモデルが判断したときに `ok: false` とともに返します。`Stop` と `SubagentStop` では、Claude Code は理由を差し戻さずにターンを終わらせます。エージェントフックとその他のイベントはこのフィールドを無視します。

## 4. フックの標準出力の解釈とスキルのフックの寿命が明文化された

終了コード 0 の節に、Claude Code が標準出力を何として読むかの判定が加わりました。先頭の空白を無視して、`{` で始まる出力は JSON として解析し（正しい JSON でなければプレーンテキスト扱いに落ちます）、それ以外で始まる出力は JSON 配列や引用符付きの JSON 文字列も含めてプレーンテキストとして扱います。この判定に合わせてページ全体が書き直され、これまで「正しい JSON」と書かれていた箇所は「スキーマ検証を通った解析済みオブジェクト」に統一されました。その他の終了コードの節はプレーンテキスト扱いの規則を参照する形になり、`SessionStart`・`UserPromptSubmit`・`Setup` の決定制御の節も「フックが標準出力に書いた任意のテキスト」という書き方をやめて同じ規則を指すようになっています。

**スキルとエージェントのフック** は 2 つの寿命に分かれました。サブエージェントのフックはそのサブエージェントが動いている間だけ動き、終了時に登録が解除されます（`Stop` は完了時に発火する `SubagentStop` に変換されます）。スキルのフックは、あなたか Claude がそのスキルを呼び出した時点で登録され、**セッションの残り全体で動き続けます**。スキル自身のターンより後のターンでも動くため、1 回だけ動かしたい場合は `once: true` を設定します。フックを定義できる場所の表も、この違いを表せるようにスキルの行とサブエージェントの行に分割され、スキルのページの `hooks` フロントマターの説明も同じ内容に書き換えられました。

`TaskCreated` の決定制御も変わりました。終了コード 2 または `{"decision": "block", "reason": "..."}` でブロックすると、Claude Code はタスクを削除し、メッセージをツールのエラーとして Claude に返します。`continue: false` は無視されるため Claude は作業を続けます。従来は `continue: false` でチームメイトごと停止する仕様でした。決定制御の表でも `TaskCreated` が `TeammateIdle`・`TaskCompleted` と同じ行から独立しています。エージェントフックの扱いも明確になり、`ok: false` のときは同じイベントで `continueOnBlock: true` を付けたプロンプトフックと同じ扱いになること、エージェントフックには `continueOnBlock` フィールドが無く `impossible` にも対応しないことが明記されました。MCP ツールフックの出力も、コマンドフックの標準出力と同じ解析規則に従うと書き直されています。

## 5. GitLab のマージリクエストに対応した

`--worktree` がマージリクエストを受け付けるようになりました。`#` を前置した番号、GitHub のプルリクエスト URL に加えて、`https://gitlab.com/group/repo/-/merge_requests/123` のような GitLab のマージリクエスト URL を渡せます。Claude Code は URL からは番号だけを読み、取得は常に `origin` から行い、取得パスは `origin` のホストで決めます。github.com なら `pull/<number>/head`、gitlab.com なら `merge-requests/<number>/head`、GitHub Enterprise や自己管理の GitLab などその他のホストでは `pull/` を先に試してから `merge-requests/` を試します。worktree の作成先は従来どおり `.claude/worktrees/pr-<number>` です。v2.1.233 より前は `#<number>` と GitHub 形式の URL しか受け付けず、常に `pull/<number>/head` を取得していました。同じ書き換えで再利用の規則も整理され、ベース参照から作り直す条件はプルリクエストとマージリクエストの両方に言及するようになり、古い先端で開き直すケースは 4 項目の箇条書きになりました。

エージェントビューは GitLab 独自の記法でマージリクエストを表示します。マージリクエストに紐づいたセッションの行の右端には `#1234` ではなく `!1234` のラベルが付き、フィルタとディスパッチの入力欄はマージリクエストの URL を受け付け、貼り付けると新しいセッションを起動する代わりにそのマージリクエストで作業中のセッションの行が選ばれます。v2.1.233 より前はラベルが `#1234` で描画され、貼り付けた URL は最初のプロンプトにその URL を含むセッションにしか一致しませんでした。

worktree にはもう 1 つ、GitLab とは無関係の変更があります。`-p` の実行は終了時のプロンプトが無いため worktree が掃除されませんが、作成時に取ったロックも、後のセッションによる古いロックの掃除まで残ったままになります。そのため `git worktree remove` がロックを理由に拒否したら、先に `git worktree unlock` を実行する必要があります。

## 1. 権限モードを選択する

追加 102 行・削除 44 行。中身はハイライト 1 のとおりで、**セッションがどのモードで始まるか** と **別の権限モードで開始する** の 2 節の新設、組み込み既定の 6 行の表、VS Code 拡張の 4 段の解決順が中心です。ほかに 2 点、書き換えがあります。冒頭は「Claude がどのくらいの頻度で一時停止するか」を説明する文章から、権限モードとは何かを定義する文章に書き直され、Pro・Max・Team プランでは auto モードが組み込みの開始モードだと明言されました。プロジェクト設定の `defaultMode: "auto"` に関するトラブルシューティングからは、リポジトリが自分に auto モードを付与できないようにするため、という理由付けが消え、単にそれらのファイルからは値が効かないという書き方になっています。

プロバイダー向けの節も書き換えられました。Bedrock・Agent Platform・Foundry・サインイン済みの apps gateway セッションでは auto モードが既定で `Shift+Tab` のサイクルに現れますが、それは開始モードを変えません。これらのプロバイダーではターミナルのセッションは `defaultMode`（変更しない限り Manual）で始まり、VS Code 拡張の会話は `claudeCode.initialPermissionMode` か拡張で選んだモードが指定しない限り Manual で始まる、と明示されました。

## 2. Hooks リファレンス

追加 67 行・削除 56 行。中身はハイライト 4 のとおりです。それ以外では、フックを定義できる場所の表でスキルとサブエージェントの行が 2 つに分かれ、スコープ列にスキルのフックはセッションの残り全体、サブエージェントのフックは実行中だけ、と書き分けられるようになりました。プロンプトフックのレスポンススキーマには `/goal` の新しい判定を支える `impossible` フィールドが加わり（ハイライト 3 参照）、停止前に 3 つの条件を確認する例も、モデルが `ok: false` を返すのは「条件がまだ満たされていないから」という書き方に改められています。

## 3. カスタムサブエージェントの作成

追加 39 行・削除 24 行。新設の **サブエージェントの名前** とチームメイト化の帰結はハイライト 2 のとおりです。残りの多くは、終了したサブエージェントが画面からどう消えるかの話です。バックグラウンドのサブエージェントが正常に終了すると、Claude Code はパネルからその行を直ちに取り除き、スクリーンリーダーモード以外ではフッターに `/tasks to see subagents` を 30 秒間表示します。その 30 秒の間に `/tasks` を実行して `Enter` を押すとトランスクリプトを開けます。失敗した場合と自分で止めた場合は行が 30 秒残り、`x` で早く消せます。v2.1.232 より前は、正常終了したサブエージェントの行も失敗時と同じく 30 秒残り、フッターの案内はありませんでした。同じ規則は **実行中のフォークを観察して操縦する** でフォークについても繰り返され、パネルのキー操作の表の `x` の行も、実行中なら停止・実行中でなければ行を消す、という書き方に直されました。

細かい変更もあります。`--agents` の JSON が受け付けるフィールドの一覧から `color` が外れ、`--append-subagent-system-prompt` はフォークしたサブエージェントには適用されない（フォークは会話自身のプロンプトを引き継ぐため）と明記されました。フロントマターの `permissionMode` の説明も新しい開始モードを前提に書き直され、未設定ならメイン会話のモードを引き継ぎ、それは Pro・Max・Team プランでは auto モードから始まると説明されたうえで、`default` は Manual モードだと明示されています。ネストしたサブエージェントの節からは「v2.1.193 以降」という注記が消え、**フォークと名前付きサブエージェントの違い** は **フォークと他のサブエージェントの違い** に改称されて、本文の「名前付きサブエージェント」も「フォーク以外のサブエージェント」に置き換えられました。
