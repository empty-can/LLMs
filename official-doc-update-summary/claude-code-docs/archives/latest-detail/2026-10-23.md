## 1. MCP サーバーが長い仕事を自分で動かす MCP タスクの節群が載った

**`mcp` に h3「MCP tasks that run on the server」ができました。** MCP タスクは、レポートの書き出しやビルドのような長い仕事を、MCP サーバーが [MCP の tasks 拡張](https://modelcontextprotocol.io/extensions/tasks/overview)で自分で動かすものです。Claude のツールの呼び出しはサーバーが仕事を受け付けた時点で返るので、待たせない限り Claude は作業を続け、仕事が終わるとトランスクリプトにそう出て Claude が結果を受け取ります。その間フッターには `1 MCP task` のような数が出て、Claude Code はサーバーに状態を尋ねてタスクを追います。リモートのサーバーのタスクは Claude Code を終了しても動き続け、同じセッションを再開すれば追い直せます。Claude Code の CLI ではパブリックベータで、v2.1.304 以降が要ります。7 つの h4 は次のとおりです。

- **「Stop an MCP task or get its result」**: `/tasks` でタスクを選んで `x` を押すか Claude に頼むと、Claude Code は追うのをやめてサーバーに取り消しを頼みます（サーバーが仕事を終えてしまうこともある）。切れたサーバーは先に `/mcp` でつなぎ直さないと取り消しが送られず、Claude Code はタスクを忘れて追い直せません。`Esc` ではバックグラウンドのタスクは止まりません。終わると `MCP task <server task id> (<server>/<tool>) completed.` の行が出ますが、結果はトランスクリプトではなく Claude に届くので Claude に尋ねます（Claude が手すきなら頼まれなくても取りかかる）
- **「Answer a question from an MCP task」**: 動いているタスクは入力を求める elicitation のダイアログを開けます。`/tasks` を開いている間は隠れるので、閉じて答えます。非対話のセッションでは、入力を求めたタスクを、`Elicitation` フックや Agent SDK の `onElicitation` を呼ばずにサーバーに取り消させます
- **「Exit, clear, or resume while an MCP task runs」**: どの終了の選択もリモートのサーバーのタスクを取り消しません。stdio のサーバーのプロセスは Claude Code の終了で止まるので、そのサーバーの文書が仕事がプロセスより長く続くと言っていなければ、終わらせるか `/tasks` で止めてから終了します。`/clear`・`/branch`・別のセッションの `/resume` では、Claude Code が開いている間は今の会話に結果が届きます。`claude --resume`・`claude --continue`・`/resume` でタスクを始めたセッションに対話的に戻ると、サーバーがつながったところで追い直します。一回きりの `claude -p "<prompt>"` での再開、新しいセッション、`--fork-session` では追いません
- **「What a call needs to become an MCP task」**: サーバーがタスクに対応していること、protocol revision 2026-07-28 でつないだ HTTP・stdio・claude.ai のコネクターのサーバーであること（`MCP_SDK_GENERATION=v1` か `MCP_PROTOCOL_NEGOTIATION=legacy` で外れる）、機能フラグを取得するセッションであること（Amazon Bedrock などのサードパーティのプロバイダーや、テレメトリーかフラグの取得がオフでは不可）、Anthropic がそのセッションの種類で有効にしていること（v2.1.304 以降のターミナルの CLI・Agent SDK・GitHub Actions。VS Code の拡張機能とデスクトップアプリにはない）、サブエージェントではなくメインの会話からの呼び出しであること、そして対話的なセッションか、`CLAUDE_AUTO_BACKGROUND_TASKS` が `1` などの条件を満たす Agent SDK か `--input-format stream-json` の `claude -p` の実行であることが、すべて要ります
- **「Status messages on an MCP task」**: Claude Code がサーバーかタスクに届かないときの `/tasks` の項目か最後の行のメッセージと対処の表です。`reconnecting…`、`needs a sign-in to <server>`、エラーの応答の再試行、300 秒で諦めた 3 つのメッセージ、サーバーがこのセッションに設定されていない・接続の設定が変わった、タスクの ID を拒まれた、が並びます。`outcome unknown.` で終わる行は Claude Code が追うのをやめたことを示し、呼び出し直すと仕事が繰り返されうるので、先にサーバーで何が済んだかを確かめます
- **「Time limits on MCP tasks」**: 既定では、バックグラウンドのタスクに Claude Code の時間の上限はありません。ツールの呼び出しの上限（全体の時間の上限とアイドルのタイムアウト）は、サーバーが呼び出しにタスクで答えるまでかかり、Claude を待たせたときはタスク全体にかかります
- **「Make Claude wait for the result of an MCP task」**: 対話的なセッションで結果を待たせるには、`CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS` を `0`（すべての MCP のツールの呼び出しを終わるまで待つ）か、新しい `CLAUDE_CODE_DISABLE_MCP_TASK_BACKGROUND` を `1`（タスクの結果を待つが、自動のバックグラウンド化がオンなら既定の 2 分で呼び出しを通常のバックグラウンドの呼び出しに移す。それはセッションの終了を越えない）にします。待つ間に `Esc` を押すか上限に達すると呼び出しが終わり、サーバーに取り消しを頼みます。`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` やベアモードだけでは待ちません

**サーバーを作る人向けの h3「MCP tasks for server authors」もできました。** protocol revision 2026-07-28 の接続では、各要求の `params._meta["io.modelcontextprotocol/clientCapabilities"]` の `extensions` に `"io.modelcontextprotocol/tasks": {}` が入ります。h4「Answer the call with a task」によると、この拡張がある `tools/call` にだけ `"resultType": "task"` のタスクで答え、ないのに答えるか必須のフィールドが欠けると Claude は `Unsupported result type 'task' for tools/call` のツールのエラーを受け取ります。必須は `taskId`（128 文字までの空白なしの印字可能な ASCII）・`status`・`createdAt`・`lastUpdatedAt`・`ttlMs`（`null` 可）で、`pollIntervalMs`（250〜30000 に収め、ないときは 2000）と `statusMessage` は任意です。HTTP とコネクターのサーバーでは要求ごとのタイマーの内に答え始める必要があるので、仕事を受け付けて先に答え、それから仕事をします。h4「Report status, results, and questions」によると、Claude Code はその後 `tasks/get` をポーリングの間隔ごとに送り、`"resultType": "complete"` の応答の `status` で扱いを変えます。

- **`completed`・`failed`・`cancelled`**: `completed` は最上位の `result` を通常の `tools/call` の結果として Claude に渡し（中の `isError: true` は失敗）、`failed` は最上位の `error` の `message`（なければ `statusMessage`、それもなければ `Task failed`）を、`cancelled` は `statusMessage`（なければ `Task was cancelled by the server`）を伝えます
- **`input_required`**: `inputRequests` の各キーに `tasks/update` の `inputResponses` で 1 回ずつ答えます（1 タスク 16 キーまで）。`elicitation/create` は対話的なターミナルのセッションだけ、`roots/list` はどこでも応じ、応じられない要求ではサーバーにタスクの取り消しを頼みます
- **そのほか**: JSON-RPC のエラー `-32602` は未知のタスクの ID と読み、バックグラウンドのタスクなら 5 分まで尋ね続けてから結果不明と伝えます。`tasks/cancel` はサーバーがつながっている間にタスクを止めたときに送り、終了時には送りません。`tasks/result`・`tasks/list`・`notifications/tasks` は使わないので、結果は `tasks/get` の応答に入れます

**ほかのページも追従しています。**

- **`env-vars`**: `CLAUDE_CODE_DISABLE_MCP_TASK_BACKGROUND`（v2.1.304 以降）が加わり、`CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS` の `0` は対話的なセッションで MCP タスクも待たせる、と加わりました。機能フラグの取得をオフにするとできないことにも MCP タスクが加わっています
- **`headless`**: 新しい h4「MCP work when a non-interactive run ends」によると、`claude -p` の実行はバックグラウンドの MCP の仕事を待ちません。リモートのサーバーの MCP タスクは続き（追い直すには一回きりの `claude -p "<prompt>"` ではなくそのセッションを再開する）、自動のバックグラウンド化で移った MCP の呼び出しの結果は失われます
- **`claude-directory`**: `projects/<project>/<session>/mcp-tasks/` に、再開したセッションが動いているタスクを追い直すのに要るものと、Claude がまだ読んでいない終わったタスクの結果が置かれる、と載りました
- **`mcp` の「Automatic backgrounding of long tool calls」**: `/tasks` の詳細に `runs on the server; survives exiting this session` と出るバックグラウンドの呼び出しは MCP タスクだ、という案内が冒頭に加わりました

## 2. デスクトップでコマンドが出力したホストへの SSH 接続と踏み台ホストの許可が載った

**`desktop` の「SSH sessions」に h4「Create an SSH connection from a command」ができました。** コマンドラインのツールがリモートマシンをオンデマンドで作るなら、そのコマンドを `~/.claude/settings.json` の `sshHostCommands` に加えます。環境セレクターにはエントリーの名前を付けた項目（例: **Create Dev box**）が出て、選ぶと Desktop が手元のコンピューターでコマンドを動かし、コマンドが出力したホストを SSH 接続として保存してつなぎます。Claude Desktop v3.6556.0 以降の macOS か Linux で、Claude アカウントでサインインしている必要があります。1 つのエントリーが 1 つの接続で、ホストは一度に 1 つです。コマンドが動くのは接続を作るときとホストを差し替えるときだけで、つなぐたびではありません。

**Desktop はマシンを止めも消しもしない、と警告しています。** 差し替えたホスト、ファイルから外したか `id` を変えたエントリーのホスト、コマンドが作ったのに Desktop がホストを保存しなかったマシン（コマンドの失敗か時間切れ、出力されたホストが使えないか使用中か組織が許さない、実行中に取り消したかエントリーを変えたか Desktop を終了した）は、自分のツールで消すまで動き続け、費用がかかりえます。エントリーのフィールドは `id`（必須。64 文字までの ASCII の英数字と `.`・`_`・`-`。ほかのエントリーや `sshConfigs` と重ねない。Desktop は接続のホストをこの下に保つので、変えると接続はホストなしでやり直しになり、古いマシンは動き続ける）・`name`（必須）・`command`（必須）・`sshIdentityFile`・`startDirectory` です。変更と削除はファイルで行い（アプリの SSH の接続のダイアログは開かない）、編集の後に Desktop を再起動する必要はありません。5 つの h5 は次のとおりです。

- **「Write the command」**: Desktop はシェルも端末もなしでプログラムを直接起動します。プログラムは名前か `/` からの完全なパスで書き（名前はログインシェルが export する `PATH` で探す。`./acme-dev` のような相対パス・`~` で始まるパス・エイリアス・関数は使えない）、コマンドに使えるのは空白・ASCII の英数字・`+,-./:=@_~` だけです。引用符・パイプ・変数・`?` か `&` のある URL などが要るならスクリプトに入れ、実行可能にして `#!` 行で始め、`command` にその完全なパスを書きます（macOS では Documents・Desktop・Downloads のフォルダーに置かない）。入力も端末もないのでプロンプトは出せず、ブラウザーかプロンプトでのサインインは先にターミナルで済ませます。プログラムはホームディレクトリで、ログインシェルが export する変数とともに動き、10 分たっても動いていれば止められます。終了コード 0 で、標準出力にホストだけ（`host` か `user@host` の 1 行、またはポートを名指せる `{"sshHost": "...", "sshPort": 2222}` のような JSON。`startDirectory` も入れられる）を出す必要があり、ほかの行を出すツールを包んで最後の行だけを出すスクリプトの例が載っています
- **「Connect to a new host」**: 新しいホストへの最初の接続では、ホストの鍵の指紋（OpenSSH の既定の確認）と、開くフォルダーを信頼するかを尋ねられます。鍵の質問を飛ばすには、コマンドがホストを出す前に、ツールがマシンを作ったときに知った鍵を `~/.ssh/known_hosts` に加えます。`StrictHostKeyChecking` が `no` か `accept-new` で `UserKnownHostsFile` も `/dev/null` か `none` だと鍵が記録されず、ツールが名前を使い回すと警告なしに別のマシンにつながりうる、と注意しています
- **「Replace the host」**: ホストができると、項目は **Replace Dev box's host** になります（一覧になければ **More** の下）。マシンがなくなったか新しくしたいときに選ぶと、Desktop がコマンドを動かし直し、新しいセッションは新しいホストを使います。保存から 10 分は灰色で、その間は新しいホストが答えなくても新しいセッションのページがつなぎ続けます。古いホストのセッションはそこに残り、続けるにはセッションを開いて **Add SSH connection** で古いホストを別の接続として保存します
- **「Distribute commands to your team」**: 管理者は、デスクトップアプリ自身のデバイス管理のポリシーではなく、各コンピューターの Claude Code の managed settings のファイルか MDM ポリシーで `sshHostCommands` を配ります（server-managed settings とプロジェクト・ローカルの設定のキーは無視される）。利用者のエントリーはフックと同じく扱われるので、管理者のエントリーだけにするには `strictPluginOnlyCustomization` に `"hooks"` を入れます（ユーザー・プロジェクト・ローカルの設定の Claude Code のフックも止まる）。`disableAllHooks` は管理者のエントリーも止め、`disableDesktopLocalSessions` か何も許さない `sshHostAllowlist` では Create・Replace の項目が出ません。`sshHostAllowlist` を使うなら、ツールが出力する各ホスト名にパターンを一致させます（照合はコマンドの後なので、断られたマシンはすでにできている）。配った後はテスト用のコンピューターで Desktop を再起動して確かめます
- **「If a command is missing or gray」**: 項目が出ない場合（設定ファイルの JSON かスキーマの誤り、キーの綴りの誤り、プロジェクトの設定に置いた、Windows かサードパーティのプロバイダー、組織がローカルか SSH のセッションをオフにした、`ssh` のプログラムがない）と、灰色の場合（エントリーの誤り、自分の設定ファイルの破損、10 分以内の新しいホスト、フックがオフか制限されている、server-managed settings の読み込み中）の対処です

**`sshHostAllowlist` には h5「Allow jump hosts」ができました。** Claude Desktop v3.1623.0 以降は、利用者の `~/.ssh/config` がセッションのホストに設定する `ProxyJump` か `ssh -W %h:%p <host>` の形の `ProxyCommand` の踏み台ホストも、それぞれの解決後の `HostName` で一覧に照らし、一覧にないと接続か再接続が失敗します（エラーの詳細が加えるべき `HostName` を示す）。一覧には 1 種類の項目しかないので、一覧の踏み台ホストでは利用者がセッションも始められると警告し、利用者が更新する前に `ssh -G` で経路と各踏み台ホストの `hostname` を調べて加える 3 つの手順を載せています。「Restrict which SSH hosts users can connect to」の、`ProxyCommand`/`ProxyJump` のエントリーも解決後の `HostName` が一致すれば許可される、という文は、`Host` の別名に限った文と、セッションの踏み台ホストも一致が要る、という文に改められました。h5「Reach a machine behind a jump host」の例と、`sshConfigs` を配るときの確認にも、踏み台ホストを一覧に加える注記が加わっています。

## 3. どのチェックがツールの呼び出しを断ったかを示す safety_event のイベントが載った

**`monitoring-usage` の「Events」に h4「Safety event」ができました。** チェックがツールの呼び出しを断るか権限の確認を求めたとき（下記の safety event のない呼び出しを除く）、サンドボックスのネットワークプロキシが接続か要求を断ったとき、フックが結果を止めたときに記録されるイベントで、Claude Code v2.1.307 以降が要ります。ほかのイベントと一緒にエクスポートされ、専用の設定はありません。イベント自身の属性にはコマンドの文・ファイルのパス・ホスト名・MCP のサーバーとツールの名前は入りません（すべてのイベントに付く標準の属性の `workspace.host_paths` やリポジトリの属性は付きうる）。コマンドや MCP のツールを知るには、`OTEL_LOG_TOOL_DETAILS=1` にして、対応する `tool_decision` のイベントの `tool_parameters` を読みます。主な属性は次のとおりです。

- **`category`**: チェックか結果の種類（下記）
- **`decision`**: `"accept"`・`"reject"`、またはフックが結果かターンの終わりを止めたときの `"sent_back"`
- **`decision_source`・`reason_code`・`reason_type`・`rule_source`**: だれか何が決めたか（`tool_decision` の `source` の値か `"other"`）、チェックの理由（`"rule:policySettings"`・`"mode:dontAsk"`・`"hook:PreToolUse"`・`"classifier:auto-mode"` など）とその種類、関わったルールの設定のソース
- **`circuit_breaker`・`classifier_category`・`hook_event`**: 組み込みの安全のチェック（`"dangerousRemoval"`・`"outsideReadsBlocked"`・`"claudeSettingsFile"` など）、auto モードのブロックの元の組み込みのルール（`OTEL_LOG_TOOL_DETAILS=1` のとき）、フックのイベント
- **`tool_class`・`tool_name`・`tool_source`・`permission_mode`・`tool_use_id`**: ツールの種類と、チェックされた呼び出し
- **`sandbox_violation_count`・`sandbox_enabled`**: 呼び出しのコマンドからの接続か要求のうちサンドボックスのネットワークプロキシが断った数（文字列の `"0"`〜`"20"`）と、サンドボックスがオンか

**h5「Safety event categories」** の `category` は 14 種で、`"permission_rule"`（managed settings の外の deny か ask のルール）・`"managed_policy"`（managed settings の deny か ask のルール）・`"permission_mode"`（`dontAsk` か plan のモード、確認を出せないセッションでのカテゴリーのない確認）・`"hook"`・`"auto_mode_block"`・`"auto_mode_no_verdict"`・`"safety_check"`・`"static_analysis"`（解析するには複雑すぎるなど、Bash か Monitor のコマンドの書き方）・`"sandbox_override"`（サンドボックスの外で動かす確認）・`"user_rejected"`・`"sandbox_network"`・`"sandbox_other"`・`"hook_review"`・`"other"` です。h5「Calls without a safety event」は、カテゴリーのない確認に答える人がいなくて断られた呼び出し（`--permission-prompt-tool` も `--permission-prompts none` もない `-p` の実行）を、同じ `tool_use_id` の safety event のない、`"reject"` で `source` が `"config"` の `tool_decision` で探す方法と、safety event の付かない呼び出しの例を、h5「Prompts with no category」は、作業ディレクトリの中の編集での `default` モードの確認のように、どの `category` もそのチェックを名指さない確認を説明しています。

**関連する記述も改められました。**

- **`tool_decision` の `source`**: どのソースが呼び出しを断ったかを知るには、同じ `tool_use_id` の safety event の `category` と `rule_source` を読む（safety event のない呼び出しもある）、と加わりました
- **「Audit security events」の表**: どのチェックが呼び出しを断ったか確認を求めたか、フックがどの呼び出しを断りどの結果かターンの終わりを止めたか、サンドボックスのネットワークプロキシが Bash か PowerShell のコマンドの接続か要求を断ったか、の 3 行が `safety_event` で加わりました

## 5. サブディレクトリの CLAUDE.md と必要時に読む rules にファイルごとの上限ができた

**changelog の v2.1.309 に「とても大きな入れ子の CLAUDE.md の下のファイルを読んだ後、セッションが繰り返し圧縮する問題を修正。上限を超える入れ子の CLAUDE.md は先頭だけを読み込む」という項が載り、`memory` のトラブルシューティングに h3「Claude ignores the end of my subdirectory CLAUDE.md」ができました。** 必要時に読むサブディレクトリの `CLAUDE.md` か rules のファイルがファイルごとの上限を超えると、Claude はその先頭だけを受け取ります。その部分の末尾には残りを Read ツールで読むよう Claude に伝える注記が付き、Claude が読むことを選ぶまで、後ろの指示はコンテキストにありません。確かめ方と縮め方は次のとおりです。

1. **上限がかかるファイル**: Claude Code を始めたディレクトリのサブディレクトリの `CLAUDE.md` と `CLAUDE.local.md`（とそれらが `@path` で読み込むファイル）、サブディレクトリの `.claude/rules/` の rules のファイル、プロジェクトの `.claude/rules/` か `~/.claude/rules/` のパス指定の rules
2. **上限**: 20 万トークンのコンテキストウィンドウで 40,000 文字、100 万トークンのコンテキストウィンドウでは Claude Opus 4.6 と Claude Sonnet 4.6 で 200,000 文字、それより新しいモデルで 150,000 文字
3. **数え方**: Bash か Zsh で `wc -m path/to/CLAUDE.md` を実行して文字数を出す
4. **比べた結果**: 上限を超えていればファイルを削るか、一部を 1 つ以上の rules のファイルに移し（各ファイルが別々に上限に数えられる）、下回っていれば「Claude isn't following my CLAUDE.md」でほかの原因を探します

v2.1.309 より前は、必要時に読むファイルにこの上限はかかりませんでした。起動時に読み込む CLAUDE.md の扱いは変わらず、`MEMORY.md` の節の後の文は、起動時に読み込む各 CLAUDE.md は 4 MiB 以下なら全体を Claude が受け取り、それを超えるファイルは読み込まない、パス指定の rules とサブディレクトリの CLAUDE.md には別の小さい上限がある、という NOTE の囲みになりました。「My CLAUDE.md is too large」にもパス指定の rules のファイルを上限の内に保つ注記が加わり、`@path` で読み込むファイルの説明は「起動時に読み込む」から「読み込む側の CLAUDE.md と一緒に読み込む」に言い換えられています。`features-overview` の CLAUDE.md の行と説明も「起動時に読み込む各ファイルの全体」に改められ、入れ子の CLAUDE.md がファイルごとの上限を超えると Claude は先頭だけを受け取る、と加わりました。

- **そのほか**: Managed settings の表の前置きに「行が別に示すキーを除く」が加わりました。Code タブで使えないものの一覧の `/config` は **Settings > Claude Code** を開くとだけ書かれ、後ろの文が無視されるという説明が外れています。SSH のエラーの表の手元のディスクの行の文は `Free up disk space on this computer` に改められ、クラウドのセッションの説明のプロジェクトの案内は「Create a project」へのリンクになりました

## 2. Connect Claude Code to tools via MCP

ページの差分の大半は、ハイライト 1 の MCP タスクの 2 つの h3 と 9 つの h4 です。そのほかは次のとおりです。

- **新しい h4「Stdio servers that exit or fail to start」**（「Automatic reconnection」の下）: stdio のサーバーをもう一度始める方法を、Claude Code の動かし方ごとに示す表です。対話的なセッションでは、プロセスが途中で終わったときも最初の接続が失敗したときもサーバーは失敗と示され、`/mcp` のサーバーのメニューの **Reconnect** で始め直します。`claude -p` の実行と Agent SDK のセッションでは、途中で終わったサーバーは Claude が次にそのツールを呼んだときに始め直し、つながると呼び出しが動きます。最初の接続が失敗したときは、`claude -p` はそのサーバーのツールなしで続き（実行し直すと試し直す。プラグインのサーバーは失敗から 15 分は新しい実行でも接続を飛ばす）、Agent SDK はコードからサーバーをつなぎ直せます。これまでの「stdio のサーバーは手元のプロセスなので自動ではつなぎ直さない」という文はこの h4 への案内に改められ、最初の接続の再試行がかからない場合の一覧にも stdio のサーバーの最初の接続が加わりました
- **新しい h3「Time limits on MCP tool calls」**: MCP のツールの呼び出しの時間を、サーバーごとには設定のエントリーの `timeout`（ミリ秒）で、全体には `MCP_TOOL_TIMEOUT` で絞る、という前置きが付き、既存のサーバーごとの `timeout` と要求ごとのタイマーの段落がこの h3 の下になりました
- **「Automatic backgrounding of long tool calls」**: 変え方が箇条書きになり、`CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS` の `0` は対話的なセッションで MCP タスクも待たせる、`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS` の `1` はバックグラウンドのコマンドとサブエージェントと一緒に止める、と改められました
- **そのほか**: v2 のランタイムが新しい revision を尋ねるサーバーに、クラウドと Remote Control のセッションのコネクターも含まれると加わりました（`env-vars` の `MCP_PROTOCOL_NEGOTIATION` の説明も同じ趣旨で書き直された）。プラグインのサーバーの「Automatic lifecycle」には、stdio のプラグインのサーバーの接続が 15 分以内に失敗していれば接続を飛ばす、と加わっています

## 3. Error reference

ハイライト 4 の h3「Workspace not trusted when running claude ultrareview」のほかの主な変更は次のとおりです。

- **新しい h3「Skipping connection (recent failure cached; retries automatically in 15 min, or edit the plugin config to retry now)」**（「Plugin errors」の下）: プラグインが提供する stdio の MCP サーバーへの接続が 15 分以内に失敗していたため、Claude Code がサーバーを始めなかったことを示すメッセージです。セッションはそのサーバーのツールなしで続き、15 分たってもそのセッションでは試し直さず、最後の失敗から 15 分以上後に始めた新しいセッションか `claude -p` の実行で試し直します。待たずに試すには、対話的なセッションでは `/mcp` でサーバーを選んで **Reconnect**、Agent SDK のアプリでは `reconnectMcpServer()` か `ClaudeSDKClient.reconnect_mcp_server()`、`claude -p` では同じマシン・同じ OS のアカウント・同じ `CLAUDE_CONFIG_DIR` で同じプラグインを読み込む対話的なセッションを始めて `/mcp` からつなぎ直し、プラグインを作っているならサーバーの `command`・`args`・`env` を変えます。このメッセージは失敗した接続のエラーの代わりに出るもので、新しい試みも失敗すればその試みのエラーが出ます
- **「Disk full or disk quota used up」**（旧「Disk quota or temp filesystem is full」）: Claude Code の一時ディレクトリのあるボリュームの空き・inode・クォータを空ける、コマンドの結果の `Disk full:`・`Disk quota used up:`・`Nearly out of inodes:` で始まる行がそのディレクトリを名指す、と冒頭が改められ、例のメッセージは v2.1.309 の新しい形（ボリュームと空きの量を示し、`CLAUDE_CODE_TMPDIR` で別のボリュームのディレクトリを使う案内を含む）になりました。対処には `df -h <dir>`・`df -i <dir>` での確かめ方と、メッセージごとの消し方（ボリュームのどこでも要らないファイルを消す、自分のファイルを消す、数の多いファイルを消す）が加わり、v2.1.309 より前のメッセージの一覧が残っています。「Find your error」の表と `troubleshooting` の行も新しいメッセージに改められました
- **h3「Temp directory refused or cannot be created」**: ボリュームがいっぱいのときのメッセージが `Claude Code's temporary directory <dir> could not be created: the volume holding /tmp is full (ENOSPC). ...` になり、クォータを使い切った `EDQUOT` の場合の対処が加わりました（v2.1.309 より前は `ENOSPC: no space left on device, mkdir '/tmp/claude-501'` のような OS のエラーの文だけだった）
- **h3「Couldn't send feedback」**: `/feedback`・`/bug`・`/share` のダイアログの報告か、キューのフィードバックの下書きが送られなかったときの節が書き直されました。コロンの後に組織についての文が続けば組織がフィードバックを断っていて、同じ報告は同じ答えになります。対処は、サインインしていない（`/login` してから送り直す）、組織の拒否（`To report a bug, open an issue` とあれば GitHub の issue で報告する。キューの下書きはキューに残り、破棄もできる）、資格情報の拒否（`/status` でセッションが送るログイン・トークン・API キーを確かめる）、ネットワークの失敗（送り直す）、`(server returned <status>)` か理由なし（サービス自身のメッセージが続くことがある）に分かれ、GitHub の issue は公開なのでコードやトランスクリプトなど機密を書かないよう注意しています（v2.1.309 の修正に対応）
- **h3「No response from API」**: 最初のバイトの期限での再送の説明が言い換えられ、Claude apps gateway のセッションではこの期限は `CLAUDE_STREAM_FIRST_BYTE_TIMEOUT_MS` を `1` 以上にしたときだけ動く、v2.1.307 より前は gateway のセッションでこの変数を無視した、と加わりました
- **そのほか**: 「Sandbox mask files left behind at write-deny paths」（旧「Stale sandbox mask files left by a killed session」）は、殺されたセッションのほか、サンドボックスのコマンドが動いている間に終了したセッションも置き場所のファイルを残す、と改められ、v2.1.309 より前の警告の名前が注記されました（`sandboxing` の警告の名前も新しくなった）。「Couldn't confirm model with the API」のモデルの確認の待ち時間は 5 秒から 15 秒になっています
