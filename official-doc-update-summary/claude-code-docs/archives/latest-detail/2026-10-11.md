## 1. デスクトップアプリでローカルのセッションを止めて SSH の接続だけを配る構成が載った

**`desktop` の「SSH sessions」の下に「Turn off local sessions and distribute SSH connections」の節ができました。** ローカルのセッションを止め、SSH のセッションを選んだホストに限るには、`disableDesktopLocalSessions`・`sshConfigs`・`sshHostAllowlist` を一緒に配ります。例は、ローカルのセッションを止め、`dev.example.com` への接続「Shared Dev VM」（`id` は `shared-dev-vm`）を 1 つ加え、`sshHostAllowlist` をそのホストだけにする `managed-settings.json` です。

- **前提**: Claude のアカウントでサインインする利用者向けの構成です。サードパーティのプロバイダーでは SSH のセッションは既定でオフで、`sshHostAllowlist` を設定するとオンになりうるので、配る前に「SSH remote sessions in Claude Desktop on 3P」を読むよう注記されています
- **効く範囲**: どのキーもデスクトップアプリにだけ効き、ほかの使い方は変えません。開発者が自分のコンピューターで Claude Code の CLI を動かすことは止めず、Cowork のセッションと Cowork のスケジュールしたタスクにも効かず、クラウドのセッションを使えるかどうかも変えません（止めるには Admin console controls の **Cloud sessions** の設定を使う）
- **例を手直しするときの確認**: `sshHostAllowlist` のパターンが各 `sshConfigs` の項目のホスト名（`user@` を除いたもの）に一致しないと、開発者はそこに接続できません。`disableDesktopLocalSessions` には Claude Desktop v1.37937.0 以降が要ります
- **配り方**: 3 つのキーは、配る管理設定の出どころのうち最も順位の高い 1 つにまとめます。サーバー管理設定を配るなら、各コンピューターの最も順位の高い MDM の方針か管理設定のファイルにも 3 つのキーの写しを置きます。Desktop はサーバー管理設定を起動時に取りに行き、取得に成功するまではコンピューター上の写しが効くためです
- **確かめ方**: 開発者のコンピューターで Desktop を終了して開き直し、入力欄の環境のドロップダウンで **Local** が灰色になり、**SSH** の下に **Shared Dev VM** が出ることを見ます（**Local** がまだ使えるなら、Desktop の版、ファイルが正しい JSON か、そのコンピューターがどの管理設定の出どころを読むかを確かめる）。次に `other.example.com` のような許可リストにないホストで SSH の接続を加えると、Desktop は接続を保存しますが接続を断り、組織の設定がその接続を許さないと伝えます

同じページの「Pre-configure SSH connections for your team」には、`sshHost` に `user@` を書かないと、Desktop は各開発者の `~/.ssh/config` がそのホストに設定する `User` で、なければそのコンピューターでの開発者のユーザー名で接続する、という文が加わりました。

- [Desktop アプリケーション - Claude Code Docs (日本語)](https://code.claude.com/docs/ja/desktop#turn-off-local-sessions-and-distribute-ssh-connections)
- [Desktop application - Claude Code Docs (English)](https://code.claude.com/docs/en/desktop#turn-off-local-sessions-and-distribute-ssh-connections)

## 2. サンドボックスの自動許可のモードでも通常の権限の確認に回るコマンドが明記された

**`sandboxing` の「Auto-allow mode」に、自動では承認されないサンドボックスのコマンドの説明が加わりました。** サンドボックスで動くコマンドのうち、`FOO=bar npm test`（前に置いた変数の代入が、どのプログラムが動くかを変えうる）、`make CC=clang`、`eval "ls"` のようなものは、自動の承認ではなく通常の権限の確認に回ります。そのときは allow ルールと権限モードが確認を出すかどうかを決め、コマンド自体はサンドボックスの中で動きます。

この 3 つのコマンドでは、コマンドに一致する allow ルールで繰り返しの確認を止められます。

- **`Bash(make *)`**: `make CC=clang` を承認します
- **`Bash(FOO=bar npm *)`**: `FOO=bar npm test` を承認します。コマンドが変数の代入で始まるときは、ルールにその代入も含めます
- **`Bash(eval "ls")`**: `eval "ls"` を承認します。`Bash(eval *)` のようなワイルドカードのルールではこの確認は止まらないので、コマンド全体に一致するルールを書きます

コマンドに一致する allow ルールは、そのコマンドのサンドボックスの外での再試行（「The unsandboxed retry escape hatch」）も承認するので、そのコマンドは確認なしにサンドボックスの外で動きうる、という注意も加わりました。同じ節の、裸の `Bash` の ask ルール（`Bash(*)` も同じ）の説明は、「通常の権限の確認に回るコマンド」ではなく「サンドボックスの外で動くコマンド」には引き続き効く、と改められています。

ほかのページもこの節を指すようになりました。`permission-modes` の「Common setups」の表の「分類器なしにローカルで確認を減らして作業する」の行に「ほかにも確認を出しうるコマンドは Auto-allow mode を参照」と加わり、`permissions` の「How permissions interact with sandboxing」の「引き続き効く確認」の一覧に「ほかのサンドボックスのコマンドも通常の権限の確認に回りうる」の項目が加わりました。`settings-reference` の `sandbox.autoAllowBashIfSandboxed` は、`true` の説明が「`deny` のルールと内容を指定した `ask` のルールに従う」から「Auto-allow mode が述べる場合を除いて」に替わり、末尾の案内先も「Sandbox modes」から「Auto-allow mode」に改められています。

- [サンドボックス化された Bash ツールを設定する - Claude Code Docs (日本語)](https://code.claude.com/docs/ja/sandboxing#auto-allow-mode)
- [Configure the sandboxed Bash tool - Claude Code Docs (English)](https://code.claude.com/docs/en/sandboxing#auto-allow-mode)

## 3. WorktreeCreate と WorktreeRemove のフックが動く場面が広がった

**`hooks` の「WorktreeCreate」の冒頭が、フックが動く場面の一覧に書き換えられました。** これまでの `claude --worktree`、`isolation: "worktree"` のサブエージェント、自分の worktree で隔離されるバックグラウンドのセッションに、次の 3 つが加わっています。

- セッションの途中で Claude が worktree を作り、`EnterWorktree` ツールでそこに移るとき
- ワークフローが自分の worktree でエージェントを動かすとき
- `claude remote-control` が `worktree` モードで自分の worktree にセッションを始めるとき

Claude が `EnterWorktree` を呼ばずに Bash ツールで `git worktree add` を実行したときは WorktreeCreate のフックは動かないので、そのコマンドを調べたり止めたりするには `Bash` のマッチャーの PreToolUse のフックを加えるよう案内されています。

**「WorktreeRemove」にも動く場面が 3 つ加わりました。** 利用者が worktree を出て消すよう頼み Claude が `ExitWorktree` ツールで消すとき、`claude remote-control` が `worktree` モードで始めたセッションがクラッシュせずに終わり worktree に変更したファイルも未追跡のファイルも新しいコミットもないとき、それらのセッションが動いている間に `claude remote-control` を止め、同じく変更がないときです。

- **動かない場面**: サブエージェントやワークフローのエージェントが終わっても、Claude Code は WorktreeCreate のフックが作った worktree を残し、WorktreeRemove のフックを動かしません。作業が済んだら自分で消します
- **確認なしに動く経路**: `ExitWorktree` の呼び出しと `claude remote-control` の後片付けでは、フックが動く前に利用者に確認を求めません。`ExitWorktree` は呼び出しが `discard_changes: true` を渡さない限りフックが作った worktree を消すのを断るので、その経路ではフックが最後の確認になります
- **WorktreeRemove のフックがないとき**: 経路ごとに書き分けられました。worktree のセッションを出るときと `ExitWorktree` では、WorktreeCreate のフックが返したパスを `git worktree remove --force` と同じように消します（git が認識しない worktree はディスクに残る）。`claude remote-control` の後片付けでは worktree はディスクに残り、`claude remote-control` を動かしている端末に `worktree removal failed, kept: <path>` が出ます。バックグラウンドのセッションの削除は agent view の「What deleting a session removes」に従います
- **フックが 0 以外で終わったとき**: 「WorktreeRemove input」の一覧に、`claude remote-control` の後片付けの途中なら端末に `worktree removal failed, kept: <path>` が出る、と加わりました。バックグラウンドのセッションの削除での確認の説明も「その経路では」と範囲が限られています

関連して、`remote-control` の `--spawn` の `worktree` は「git のリポジトリか WorktreeCreate のフックが要る」に改められ、`worktrees` の「Isolate subagents with worktrees」には、WorktreeCreate のフックが作った worktree の扱いは WorktreeRemove を参照、という文が加わりました。

- [Hooks リファレンス - Claude Code Docs (日本語)](https://code.claude.com/docs/ja/hooks#worktreecreate)
- [Hooks reference - Claude Code Docs (English)](https://code.claude.com/docs/en/hooks#worktreecreate)
- [Hooks リファレンス - Claude Code Docs (日本語)](https://code.claude.com/docs/ja/hooks#worktreeremove)
- [Hooks reference - Claude Code Docs (English)](https://code.claude.com/docs/en/hooks#worktreeremove)

## 4. Agent SDK のタスクのメッセージに実行ごとの run_id が加わった

**`agent-sdk/typescript` の `SDKTaskStartedMessage` に `run_id` の説明ができました。** `run_id` はタスクの 1 回の実行を示します。Claude が再開したサブエージェントのように同じ `task_id` でタスクがもう一度動くと、新しい実行には新しい `run_id` が付きます。Agent SDK v0.3.292 以降が要ります。使い方として次の 3 つが挙がっています。

- **メッセージを実行に結び付ける**: 1 回の実行の `task_started`・`task_progress`・`task_updated`・`task_notification` のメッセージは同じ `run_id` を持ちます。各 `SDKBackgroundTasksChangedMessage` のその実行の項目にも、その実行の通知を届けるユーザーメッセージの origin の `runId` にも同じ値が入ります
- **遅れて届いたメッセージを見分ける**: 同じタスクの実行 ID を単なる文字列として比べると実行の始まった順に並ぶので、表示中の実行より前に並ぶ `run_id` のメッセージは以前の実行のものです。この比較以外では値の中身に意味を持たせないよう求めています
- **`task_id` に戻る**: 再開したセッションが前のプロセスの始めたタスクを閉じるために出す `task_notification` のように `run_id` のないメッセージは、`task_id` で振り分けます

例として、一度再開されたバックグラウンドのサブエージェントの 3 つのメッセージ（同じ `task_id` の 2 つの `task_started` と、最初の実行の ID を持つ `task_notification`）が示されています。型の定義では `SDKTaskStartedMessage`・`SDKTaskNotificationMessage`・`SDKTaskProgressMessage`・`SDKTaskUpdatedMessage` と `SDKBackgroundTasksChangedMessage` の `tasks` の各項目に `run_id?: string` が加わり、それぞれの説明文から `SDKTaskStartedMessage` への案内が付きました。

**`SDKMessageOrigin` の `task-notification` にも `runId?: string` が加わりました。** 「Task-notification subkinds」に、バックグラウンドのタスクの実行の通知がユーザーメッセージとしてセッションに届くと、その `task-notification` の origin の `runId` が同じ値を持つ、と加わっています。次の実行が始まった後に届いた通知も前の実行の ID を持つので、ターンがどの実行のものかは `task_id` ではなく `runId` で比べます（TypeScript Agent SDK v0.3.292 以降）。

- [Agent SDK reference - TypeScript - Claude Code Docs (English)](https://code.claude.com/docs/en/agent-sdk/typescript#sdktaskstartedmessage)
- [Agent SDK リファレンス - TypeScript - Claude Code Docs (日本語)](https://code.claude.com/docs/ja/agent-sdk/typescript#task-notification-subkinds)

## 5. 定期タスクの遅延の説明が改められ 5 分ごとのタスクの扱いが加わった

**`scheduled-tasks` の「Jitter」が書き換えられました。** 定期タスクは遅れて動きますが、`*/5 * * * *` と書いた 5 分ごとのタスクは例外になりました（1 回限りのタスクが正時や 30 分に予定されていると少し早く動く点は変わらない）。「How late a recurring task runs」では、5 分ごとのものを除き、定期タスクの各実行は次の実行までの間隔の半分まで、最大 30 分遅れて始まる、とされ、次の 3 つの場合に分けて説明されています。

- **間隔が均等な実行**: 毎時・毎日・10 分ごとのように間隔が揃ったタスクは、セッションが何もしていないときも含め、毎回同じ分数だけ遅れます
- **間隔が不揃いな実行**: 毎時 `:00` と `:15` に予定したもののように間隔が揃わないタスクは、実行ごとに遅れの分数が変わりえます
- **5 分ごと**: `*/5 * * * *` と書いたタスクは遅らせません。前回のちょうど 5 分後に動くと 5 分のプロンプトキャッシュが切れた後に始まってしまうので、各実行を 15 秒早めます

遅延の表も「Schedule」と「When each run starts」の列に改められ、先頭に「5 分ごと（`*/5 * * * *` と書いたもの。`/loop 5m` が作るのはこれ）: 前回の実行の 4 分 45 秒後」の行が加わりました。10 分ごと（0〜5 分遅れ）、30 分ごと（0〜15 分遅れ）、毎時かそれより少ない頻度（0〜30 分遅れ）の値は変わりません。「定期タスクを作ると固定の遅延が与えられ、その遅延はタスクの ID から決まる」という説明は外れています。

- [スケジュールでプロンプトを実行する - Claude Code Docs (日本語)](https://code.claude.com/docs/ja/scheduled-tasks#how-late-a-recurring-task-runs)
- [Run prompts on a schedule - Claude Code Docs (English)](https://code.claude.com/docs/en/scheduled-tasks#how-late-a-recurring-task-runs)

## 1. Debug your configuration

**「Test against a clean configuration」が、3 つの手順（Steps）に組み直されました。** セーフモードでも問題が残るときや設定そのものが疑わしいときに、自分の構成を何も読み込まないセッションを始めて問題がついてくるかを確かめる手順です。これまでの `cd /tmp && CLAUDE_CONFIG_DIR=/tmp/claude-clean claude` の 1 行と、`.claude` のフォルダー・`.mcp.json`・`CLAUDE.md` のないディレクトリから起動してプロジェクトの構成を避ける、という説明が置き換わっています。

1. **空のディレクトリを作って移る**: Claude Code のセッションを動かしていないシェルで、Bash か Zsh なら `mkdir -p ~/claude-clean/empty && cd ~/claude-clean/empty`、PowerShell なら `New-Item` と `Set-Location` で `$HOME/claude-clean/empty` を作って移ります
2. **きれいな構成のディレクトリで起動する**: `CLAUDE_CONFIG_DIR` を `~/.claude` の代わりの新しいディレクトリにし、`--setting-sources user` を渡して `.claude/settings.json`・`CLAUDE.md`・`.mcp.json` のようなプロジェクトの構成を止めます。Bash か Zsh では `CLAUDE_CONFIG_DIR=~/claude-clean/config claude --setting-sources user` で、変数はその 1 回の起動にだけ効きます。PowerShell では `$env:CLAUDE_CONFIG_DIR` を設定してから `claude --setting-sources user` を実行し、変数はその PowerShell のセッションの間ずっと残るので、元のディレクトリに戻すには次の起動の前に `Remove-Item Env:CLAUDE_CONFIG_DIR` を実行します。初回の起動で初期設定の画面がまた出れば、きれいな構成のディレクトリが効いている印です。管理設定は引き続き効き、claude.ai のアカウントでログインするとコネクターも読み込まれます
3. **問題を再現する**: きれいなセッションで問題が消えたなら、原因はユーザーかプロジェクトの構成にあります。`~/.claude.json` と `~/.claude` のファイルを 1 つずつ `~/claude-clean/config` に写し、どれでも問題が戻らなければ、同じシェルでプロジェクトのディレクトリに移って `--setting-sources user` なしで起動します（Bash か Zsh では `CLAUDE_CONFIG_DIR=~/claude-clean/config claude`、PowerShell では変数が残っているので `claude`）。問題が残るなら原因はユーザーとプロジェクトの構成の外にあるので、セッションで `/status` を実行して管理設定を確かめ、シェルの環境変数を確かめ、「Troubleshooting」に進みます

これまでの、管理設定は構成のディレクトリの外にある MDM のプロファイル・レジストリの方針・`managed-settings.json` から読まれ、サーバー管理設定も資格情報を得た後にもう一度取りに行く、という説明と、「もう一度ログインを求められる」という項目は外れています。
