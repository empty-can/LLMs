## 1. 新しいモデルではタスク追跡ツールが提供されなくなった

ツールリファレンスに **Task tool availability** 節が新設されました。Claude Code v2.1.233 以降、Opus 4.8・Sonnet 5・Fable 5・Mythos 5 とそれらのファミリーのそれ以降のバージョンでは、`TodoWrite`・`TaskCreate`・`TaskGet`・`TaskUpdate`・`TaskList` がオプトインしない限り提供されません。理由は 2 つ挙げられています。これらのモデルは書かれたチェックリストが無くてもマルチステップの作業を追えること、そしてツールの定義とリマインダーがコンテキストを占めることです。ツールが無いあいだ、Claude は作業中にタスクリストへ何も追加しません。Opus 4.7 のようなそれ以外のモデルでは従来どおり 4 つの Task ツールが既定で提供され、`TodoWrite` は `CLAUDE_CODE_ENABLE_TASKS=0` を設定したときだけ提供されます。

対象モデルでもツールを使いたい場合のオプトインは 3 通りです。Claude Code を起動する前に `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` を export する方法（例: `CLAUDE_CODE_ENABLE_TODO_TOOLS=1 claude`）で、これは全てのモデル・全てのプロバイダーで同じツールを提供します。`--allowedTools` にいずれかのツールを名指しする方法（例: `claude --allowedTools TaskCreate`）。`--tools` に列挙する方法で、こちらはセッションの組み込みツールを列挙したものだけに制限するため、使いたいツールを他の組み込みツールと並べて書く必要があります。Agent SDK の `allowedTools` と `tools` オプションも同じ働きをします。

例外と波及も整理されました。バックグラウンドセッションとウェブの Claude Code では、対象モデルかどうかに関わらず同じツールが提供されます。サブエージェントには、あなたのセッションがツールを持っているときだけ与えられ、これはサブエージェントが別のモデルで動く場合も同じです。エージェントチームのチームメイトも、同一プロセスで動くものはセッションに追従し、独立したペインで動くものは別プロセスなので自分のモデルで決まります。Task ツールが無いエージェントは、共有タスクリストではなくメッセージでチームと協調します。ツール一覧表では 4 つの Task ツールの説明に「対象モデルではオプトインしない限り提供されない」旨が加わり、`TodoWrite` の行の `CLAUDE_CODE_ENABLE_TASKS=0` も「タスク追跡ツールがあるセッションで再び有効にする」という書き方になりました。環境変数のページには `CLAUDE_CODE_ENABLE_TODO_TOOLS` が追加され（v2.1.233 以降が必要）、`CLAUDE_CODE_ENABLE_TASKS` の説明は「ツールがあるセッションの中で Task ツールと `TodoWrite` のどちらを提供するかを選ぶもの」に再定義されています。

## 2. 共有タスクリストを前提にした説明が条件付きになった

タスクリストが常にあるとは限らなくなったため、それを前提にしていた記述が各所で条件付きに書き換わりました。インタラクティブモードのタスクリストの節には、対象モデルでは Claude が書かれたチェックリスト無しで作業を追うため Claude Code がリストを埋めるツールを提供せず、リストは空のままになる、という前置きが加わりました。そのうえで、`Ctrl+T` での切り替えやタスクの共有といった従来の説明は「それ以前のモデル、およびオプトインした後」の挙動として示されています。

エージェントチームのページでは、サブエージェントとの比較表の **Coordination** 行が「共有タスクリストによる自己協調」から「メッセージによる自己協調と、Task ツールを持つエージェント向けの共有タスクリスト」に変わりました。同じ表は Claude Code を拡張するページにもあり、そちらの 2 箇所も揃えられています。タスクの割り当てと要求の節には、Task ツールを持たないエージェントは共有タスクリストではなくメッセージで協調する、という一文が加わりました。コンテキストと通信の節の **共有タスクリスト** の項目も、状況を見てタスクを要求できるのは Task ツールを持つエージェントだと限定されています。チームを最初に作る手順の説明も、共有タスクリストが作られるのは Task ツールがあるセッションの場合、という書き方になりました。

サブエージェント定義をチームメイトとして使う場合の記述も具体的になりました。従来は「`SendMessage` やタスク管理ツールのようなチーム協調ツールは、`tools` が他のツールを制限していてもチームメイトには常に利用できる」と書かれていましたが、今回からは、同一プロセスのチームメイトには Claude Code が `SendMessage` を許可リストに追加し、Task ツールがあるセッションでは `TaskCreate`・`TaskGet`・`TaskList`・`TaskUpdate` も追加する、という書き方です。ほかに、サブエージェントのページには、セッションが Task ツールを持たない場合はサブエージェントにも渡されないことが明記され、Hooks リファレンスの `TaskCreated` には、Task ツールの無いセッションではこのイベントが発火しないことが加わりました。エージェントを並列実行するページの選択ガイドも、チームメイトが共有するのはメッセージが先で、タスクリストは Task ツールを持つ場合、という順序に直されています。

- [Orchestrate teams of Claude Code sessions - Claude Code Docs (English)](https://code.claude.com/docs/en/agent-teams#assign-and-claim-tasks)
- [Hooks reference - Claude Code Docs (English)](https://code.claude.com/docs/en/hooks#taskcreated)

## 3. Agent SDK にもオプトインの手順が入った

Todo リストのページに **Model availability** 節が新設されました。タスク追跡ツールが提供されないモデルでは、オプトインしない限りメッセージストリームにそれらの `tool_use` ブロックが現れません。Python の `cli_path` や TypeScript の `pathToClaudeCodeExecutable` で自前の Claude Code を指している場合は、そのインストールが提供するツールがそのまま得られます。他のモデルと同じツールを得るには 3 通りあり、`allowedTools`（Python では `allowed_tools`）にいずれかのツールを名指しする、`tools` オプションに列挙する（セッションの組み込みツールが列挙したものだけに制限されるため、使う組み込みツールを並べて書く）、`env` オプションで `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` を渡す、のいずれかです。TypeScript の `env` はサブプロセスの環境を置き換えるので `...process.env` を展開して継承した変数を残す必要があり、Python の `env` は継承した環境の上にマージされる、という違いも書かれています。

対象バージョンは TypeScript Agent SDK 0.3.233 以降、Python Agent SDK 0.2.139 以降です。TypeScript・Python の各リファレンスにある `TodoWrite` の Note も、従来の「0.3.142 以降は `TodoWrite` が既定で無効」という説明から、対象モデルでは 5 つのツールがオプトインしない限り利用できないという一覧に置き換わり、オプトインは **Model availability**、監視コードの更新は **Migrate to Task tools** を見よ、という案内が付きました。ページ内のコード例も揃って書き換えられ、`TodoWrite` を監視する例は `CLAUDE_CODE_ENABLE_TASKS: "0"` に加えて `CLAUDE_CODE_ENABLE_TODO_TOOLS: "1"` を渡す形に、Task ツールへの移行の例は `CLAUDE_CODE_ENABLE_TASKS` を設定せず `CLAUDE_CODE_ENABLE_TODO_TOOLS` だけを設定する形になっています。

オプトインが権限オプションを兼ねる点も各所に明記されました。`allowedTools`（`allowed_tools`）にタスク追跡ツールを名指しすると、Claude Code はそのセッションをオプトイン扱いにします。この副作用は TypeScript・Python のオプション表、SDK の権限ページ、カスタムツールのページ、CLI リファレンスの `--allowedTools` と `--tools` にそれぞれ加わりました。あわせて、許可リストの説明にあった「リストにないツール」という言い方は「その他のリストにないツール」に直され、名指ししたタスク追跡ツールが例外である点と整合しています。エージェントループの組み込みツール表にも、対象モデルでは `TaskCreate` と `TaskUpdate` はオプトインしたときだけ提供される、という注記が付きました。

- [Agent SDK reference - TypeScript - Claude Code Docs (English)](https://code.claude.com/docs/en/agent-sdk/typescript#todowrite)

## 4. 認識できないモデル ID の診断行が文書化された

エラーリファレンスに **Unrecognized model ID on a request** 節が新設されました。前回のサマリで v2.1.233 の changelog 項目として 1 行触れた診断行で、今回その仕様がまとまりました。Claude Code が認識しないモデル ID でリクエストを送り、その ID を認識できるモデルに対応付ける `modelOverrides` エントリも見つからなかったとき、Claude Code は次の行を書きます。リクエスト自体は設定したとおりの ID で送られ、終了もモデルの切り替えもしません。

```text
[claude-code:unrecognized_model] {"model":"my-proxy-model","query_source":"sdk"}
```

標準エラーを読むスクリプトやハーネスでは `[claude-code:unrecognized_model]` という接頭辞で照合します。接頭辞と半角スペース 1 つの後に 1 行の JSON オブジェクトが続き、将来のバージョンでフィールドが増えうるため、予期しないフィールドは無視するよう求められています。最低限含まれるのは `model`（設定したままのモデル文字列）と `query_source`（そのモデルを使ったリクエスト経路。`-p` の実行では `sdk`、サブエージェントでは `agent:` で始まる値）の 2 つです。出力先は実行の仕方で分かれ、`-p` の非対話モードでは全ての `--output-format` で標準エラーに書かれるため標準出力をそのまま解析でき、対話セッションとバックグラウンドセッションでは代わりにデバッグログに書かれます（`--debug` を付けて `~/.claude/debug/<session-id>.txt` に取得します）。行は 1 プロセスにつきモデル文字列ごとに 1 度書かれ、サブエージェントやバックグラウンドの機能が別の未知の ID を使えばそれぞれ別の行になります。

書かれない場合も列挙されました。Amazon Bedrock の `us.anthropic.claude-...` 形式の ID、`@` でバージョンを付けた Google Cloud's Agent Platform の ID、Claude のモデル ID を含む Microsoft Foundry のデプロイ名のように、認識できるモデルへ解決できるものは対象外です。Bedrock のアプリケーション推論プロファイル ARN については、ARN そのものではなく背後のモデルを見ます。打ち間違いなど解決できない ARN には行を書きません。対処は 3 つ挙げられています。LLM ゲートウェイのエイリアスなど意図して設定した ID なら、設定ファイルの `modelOverrides` にその ID を**値**とするエントリを追加します（キーには Anthropic のモデル ID を使い、`opus` のようなファミリーのエイリアスは使えません）。自分の Claude Code より新しいモデルを指す ID なら `claude update` を実行します。打ち間違いなら設定した場所（`--model` フラグ、`ANTHROPIC_MODEL` や `ANTHROPIC_DEFAULT_*_MODEL` 環境変数、`model` 設定。`query_source` が `agent:` で始まるならサブエージェントのモデル指定）を直します。v2.1.233 より前は、認識しないモデル ID でリクエストを送っても行を書きませんでした。

この追加に伴い、設定警告の節の導入文は、メッセージの多くは起動時に書かれるが、この診断行はリクエスト時に書かれる、という形に書き改められました。モデル設定のページにも 2 箇所の相互参照が入り、プロバイダーやゲートウェイがモデル名を決めるため ID の検査が効かない場合でも診断行は全プロバイダーで書かれうること、ゲートウェイのエイリアスのような ID に対しては `modelOverrides` にエントリを足せばこの行を止められることが明記されています。

- [Model configuration - Claude Code Docs (English)](https://code.claude.com/docs/en/model-config#override-model-ids-per-version)
