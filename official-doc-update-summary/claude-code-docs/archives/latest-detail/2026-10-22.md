## 1. MCP サーバーの資格情報ストアを読めないときのエラーと対処が載った

**Claude Code は OAuth の MCP サーバーへのサインインを資格情報ストアに保っており、そのストアを読めないときのエラーの節が `errors` の「Authentication errors」にできました。** changelog の v2.1.307 には前回、「macOS でログインのキーチェーンがロックされている間、`claude -p` で MCP サーバーが『needs authentication』と出る問題を修正。理由を示し、ロックを解いた後の次の実行は新しいサインインなしで接続する」という項がありました。新しい h3「Couldn't read the stored credentials for MCP server」によれば、メッセージは次の 2 つです。

- **要求が送られなかった**: `Couldn't read the stored credentials for MCP server "<name>", so the request didn't run.` の後に、`If your Mac's keychain is locked, unlock it, then try again.` か `Try again.` が続きます。保存したサインインは変わっていないので、ストアを読めるようになったら再試行し、サインインし直すのはサーバーがそれを求めたときだけです
- **資格情報なしで送られた**: macOS の `claude -p` か Agent SDK の実行では、保存したサインインなしで要求が出た後にキーチェーンが読めるようになることがあり、その要求は `A request to MCP server "<name>" was sent without your stored credentials, so the server rejected it. The credentials are available now. Try again.` で失敗します

対処は次の順です。キーチェーンのロックを解くよう求められたら、Claude Code を動かすシェルのセッションで `claude doctor` を実行し、`macOS Keychain is not writable` で始まる警告があるか、そのシェルに `claude` のコマンドがなければ、`security unlock-keychain ~/Library/Keychains/login.keychain-db` を実行します（警告がなければロックの解除は飛ばす）。次に、メッセージが出た場所でやり直します。`claude -p` ならコマンドを再実行し、対話的なセッションなら `/mcp` で失敗と出ているサーバーを再接続して Claude に再試行を頼み、動き続ける Agent SDK のアプリなら TypeScript の `reconnectMcpServer()` か Python の `ClaudeSDKClient.reconnect_mcp_server()` を呼ぶか、新しいセッションを始めます。それでもサーバーが認証を求めるなら、使えるサインインがないので、`/mcp` か `claude mcp login <name>` で対話的にサインインします。v2.1.307 より前は、ログインのキーチェーンがロックされた Mac の `claude -p` か Agent SDK の実行は、どちらのメッセージも出さずにサーバーを認証が必要と報告していました。

- **`errors` の「Find your error」の表**: 2 つのメッセージの行が加わりました
- **`mcp` の「Authenticate with remote MCP servers」**: サインイン済みの OAuth サーバーが保存したトークンを `401 Unauthorized` で拒むとトークンを更新して 1 回再試行する、という段落に、macOS の `claude -p` か Agent SDK の実行で保存したトークンを読めない間に送った要求は、この stored-credentials のエラーで失敗する、と加わりました
- **`agent-sdk/mcp` の「OAuth2 authentication」**: 認可を求められて送るトークンがないときの状態が 2 つに書き分けられました。`needs-auth` は使えるサインインがない場合で、`headers` でトークンを渡すか、実行の前に同じマシンの対話的な Claude Code のセッションでサインインします。`failed` は `McpServerStatus` の `error` が `Couldn't read the stored credentials` か `A request to MCP server` で始まる場合で、`errors` の新しい節の対処に従います（v2.1.307 より前は、Mac のログインのキーチェーンがロックされているとき `needs-auth` だった）。どちらでもエージェントの実行はそのサーバーのツールなしで続きます

## 2. 応答の前に接続が閉じた MCP のツールの呼び出しの扱いと2回呼んでも安全なツールの印が載った

**HTTP の MCP サーバーか claude.ai のコネクターへのツールの呼び出しが、サーバーが答える前に接続を失ったときの節が `errors` の「Tool errors」にできました。** changelog の v2.1.307 には前回、「呼び出しの途中で接続が閉じると、HTTP の MCP のツールの呼び出しが 2 回送られる問題を修正。再試行するのは読み取り専用か冪等なツールだけになる」という項がありました。新しい h3「MCP server connection closed before the tool call was answered」のメッセージは `MCP server "<name>" connection closed before the tool call was answered. The tool may have run: check whether it did before running it again.` で、Claude Code にはツールが動いたかが分かりません。呼び出しを繰り返すと 2 つ目の issue を作るなどツールの操作も繰り返しうるので、Claude Code が自分で呼び出しを繰り返すのは、サーバーがそのツールを繰り返して安全と示したときの 1 回だけです。

- **操作が起きたかを確かめる**: ツールが操作するサービスで、作るはずだった issue や記録があるかを見ます
- **起きていた**: ツールをもう一度動かしません。Claude はツールの結果の代わりにこのメッセージを受け取ったので、結果を Claude に伝えます
- **起きていなかった**: Claude にもう一度動かすよう頼みます。次のツールの呼び出しで Claude Code がサーバーにつなぎ直すので、先に再接続する必要はありません（その接続も失敗するなら `mcp` の「Mid-session drops of a remote server」を見る）
- **サーバーを作っていて、ツールが 2 回呼んでも安全なら**: 繰り返して安全と印を付けます（下記）

**`mcp` には、サーバーを作る人向けの h2「Mark tools that are safe to call twice」ができました。** 印を付けたツールなら、接続が閉じたときに保留だった呼び出しを、Claude Code が HTTP のサーバーか claude.ai のコネクターに新しい接続で 1 回繰り返せます。`tools/list` の項目の `annotations` で、次のどちらかを `true` にします。

- **`idempotentHint`**: ツールは何かを変えうるが、同じ引数でもう一度呼んでも安全
- **`readOnlyHint`**: ツールは何も変えない。Claude Code はこのツールの呼び出しを、ほかの読み取り専用の呼び出しと並行して動かしもします

例として、`set_issue_status` のツールに `"annotations": { "idempotentHint": true }` を付ける JSON が載っています。`errors` の「Find your error」の表にもこのメッセージの行が加わりました。

## 3. VS Code で TLS を検査するプロキシの裏で音声入力と Web タブが失敗するときの対処が載った

**`vs-code` の「Fix common issues」に h3「Dictation or the Web tab fails behind a TLS-inspecting proxy」ができました。** 音声入力か Web タブ（クラウドのセッションを一覧するタブ）が `unable to get local issuer certificate` のような証明書のエラーで失敗するなら、IT のチームから受け取るプロキシのルート CA の証明書の PEM ファイルのパスを、`~/.claude/settings.json` の `env` の `NODE_EXTRA_CA_CERTS` に設定します。changelog の v2.1.307 には前回、「[VSCode] `NODE_EXTRA_CA_CERTS` を `~/.claude/settings.json` にだけ設定すると、TLS を検査するプロキシの裏で音声入力が失敗する問題を修正」と、拡張機能自身の要求が環境かユーザーの設定で名指しした `NODE_EXTRA_CA_CERTS` のファイルを信頼するようにした変更がありました。

- **エラーの文の見つけ方**: 音声入力ではマイクのボタンが `Dictation error: WebSocket error:` の後にエラーの文を示します。Web タブはエラーの文なしで `Remote server is not connected` とだけ示すので、コマンドパレットの **Claude Code: Show Logs** で `Claude VSCode` の出力チャンネルを開き、タブの **Reconnect** をクリックして `Connecting…` が消えるまで待ち、`Error fetching remote sessions:` か `Failed to fetch organization UUID:` を探して、最も新しい行のその後の文を読みます
- **設定の書き方**: この対処には拡張機能の 2.1.307 以降が要るので、先に拡張機能を更新します。パスは `~` を使わずに完全なパスで書き、Windows のパスは `C:\\certs\\example-ca.pem` のようにバックスラッシュを 2 つずつ書きます。`/etc/ssl/certs/example-ca.pem` を指す `env` の例が載っています
- **直らないとき**: `settings.json` を保存して録音を始めるか **Reconnect** をもう一度クリックし、エラーが戻るなら出力チャンネルで `use the CA certificates file` を探します。その警告が、拡張機能がファイルを使えない理由と、どこからパスを読んだかを示します

設定した場所ごとの対処の表もあります。VS Code を起動した環境の値は、指すファイルが使えなくても `~/.claude/settings.json` の値より優先されるので、直すか外して VS Code を再起動します。`~/.claude/settings.json` の `env` の値なら、値かファイルを直します。VS Code の `claudeCode.environmentVariables`、`~/.claude.json`、プロジェクトの `.claude/settings.json` と `.claude/settings.local.json`、managed settings の値は音声入力と Web タブには効かないので、`~/.claude/settings.json` の `env` にも設定します。

この h3 へは、`vs-code` の「Fix common issues」の表と、`voice-dictation` のトラブルシューティングの新しい項目（`Dictation error: WebSocket error:` の後に証明書のエラーが続く場合）からも案内されています。

## 4. セルフホストの Stop フックのスクリプトが強化されサブモジュールの扱いと差し替えの手順が載った

**`self-hosted-environments-configuration` の「Prompt sessions to push their work」の Stop フックのスクリプト（`stop-hook-nudge.sh`）が改められました。** スクリプトは Claude Code の Bash のサンドボックスの外で動くので、git の呼び出しが、checkout の git の設定が名指すプログラムを起動しうる機能の一部を飛ばすようになりました。ただし全部ではないので、サンドボックスだけに頼らないよう注記されています。

- **強化の行**: `GIT_OPTIONAL_LOCKS=0` を export し、`git` を `command git -c core.fsmonitor= -c core.hooksPath=/dev/null "$@"` で包む関数が加わりました
- **未コミットの変更の判定**: `git status --porcelain` が `--ignore-submodules=dirty` 付きになりました

スクリプトの後には、Stop フックは Claude に促すだけで、commit と push が動くには次の準備が要る、と加わりました。git の identity（ランナーのイメージで `user.name` と `user.email` を設定するか、ランナーを `--configure-git` で始める）、push の資格情報（Anthropic が管理する git か、「Ship git config in your image」の方法）、再開したセッションのための `--push-outcome-on-release`（環境のすべてのランナーに設定し、再開したセッションは Claude がセッションのブランチに push したコミットから始まる）です。Stop フックが促すのは 1 ターンに 1 回までで、commit か push が失敗してもターンは終わるので、セッションの git のエラーを見て直します。スクリプトの `git status` は `core.fsmonitor` を飛ばすので、大きな checkout では設定の 10 秒より長くかかりえます。その場合は Stop フックの設定の `timeout` を上げてランナーを再起動します（タイムアウトしたフックは促さずにターンを終える）。

**2 つの h3 ができました。**

- **「Submodules and the Stop hook」**: Stop フックは各サブモジュールがどのコミットにいるかを調べ、中のファイルは調べません。サブモジュールの新しいコミットは、`.gitmodules` がそのサブモジュールに `ignore = all` を設定していても、親のリポジトリが記録するまで Claude に促します。サブモジュールの未コミットのファイルは促さないので、その作業はランナーのディスクにだけ残ります。サブモジュールの未 push のコミットは調べないので、親がだれも取得できないコミットを指すことがあります
- **「Replace an earlier copy of the Stop hook script」**: 手元の `stop-hook-nudge.sh` に `GIT_OPTIONAL_LOCKS` がなければ以前の写しなので、入れたすべての場所で今のスクリプトに置き換えてランナーを再起動します（Stop フックの設定は、大きな checkout で `timeout` を上げるほかはそのまま）。セッションを Bash のサンドボックスをオンにして動かしているなら今すぐ、そうでなければ次のイメージのビルドかランナーの再起動のときに置き換えます。置き換えると、サブモジュールの未コミットのファイルでは Claude に促さなくなり、`.gitmodules` が `ignore = all` とするサブモジュールの新しいコミットでは促すようになります。フックはサンドボックスの外で動くので、「Harden your deployment」のとおりセッションを隔離するよう警告しています

changelog に対応する項目はありません。

## 5. managed-mcp.json で env の中だけ変数を展開するサーバーは許可リストの対象外と載った
