## 1. MCP 仕様 2026-07-28 が公開

MCP 仕様の新リビジョン `2026-07-28` が公開され、`2025-11-25` に代わる現行版になりました。今回の対象期間の差分は、この 1 回のリリースによるものがほぼすべてです。原文 `llms.txt` の一覧でも仕様ページの URL が `/specification/2025-11-25/` から `/specification/2026-07-28/` に一斉に切り替わり、ページ構成も再編されています。

同時に、これまでバージョンを持たなかったドキュメント側の URL も `/docs/develop/build-client` から `/docs/2026-07-28/develop/build-client` のようなバージョン付きパスに変わりました。仕様だけでなくチュートリアル・学習ガイドも仕様リビジョンごとに固定されることになります。

変更内容は「Key Changes」ページに整理されており、破壊的変更 9 件・小規模変更 12 件・非推奨化 4 件が挙げられています。破壊的変更はいずれもセッションと状態の扱いに関わるもので、既存の実装は本リビジョンへの追従にあたって相応の改修が必要です。

- [Key Changes - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/changelog#major-changes)

## 2. プロトコルのステートレス化

MCP はステートレスなプロトコルになりました。`initialize` / `notifications/initialized` のハンドシェイクが廃止され、リクエストの処理に必要な情報はすべてそのリクエスト自身が持ちます。各リクエストは `_meta` に `io.modelcontextprotocol/protocolVersion`（必須）と `io.modelcontextprotocol/clientCapabilities`（必須）を載せ、`io.modelcontextprotocol/clientInfo` でクライアントを名乗ることが推奨されます。サーバー側も各結果の `_meta` に `io.modelcontextprotocol/serverInfo` を入れることが推奨されます。必須フィールドを欠いたリクエストは `-32602`（Invalid params）で拒否され、HTTP では `400 Bad Request` が返ります。

Streamable HTTP の `Mcp-Session-Id` ヘッダーとプロトコルレベルのセッションも削除されました。`tools/list` などの一覧結果は接続ごとに変わってはならず、複数リクエストにまたがる状態はサーバーが発行した明示的なハンドルを通常のツール引数として受け渡す形に改められています。ただしリクエストごとの認証情報による出し分けは、資格情報が接続状態ではなくリクエスト入力であるため引き続き認められます。

バージョン交渉のためのハンドシェイクが無くなった代わりに、サーバーは新設 RPC `server/discover` の実装が必須になりました。対応プロトコルバージョン・能力・識別情報を 1 リクエストで返すもので、クライアントからの呼び出しは任意です。呼ばずに任意の RPC を直接投げ、`UnsupportedProtocolVersionError`（`-32022`）が返ってきたら対応バージョンを選び直すこともできます。あわせて `ping`・`logging/setLevel`・`notifications/roots/list_changed` が削除されました。

- [Overview - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/basic/index#statelessness)
- [Discovery - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/server/discover)

## 3. 多段リクエスト MRTR への移行

サーバーがクライアントへリクエストを送る従来の方式が廃止され、Multi Round-Trip Requests（MRTR）パターンに置き換わりました。`roots/list`・`sampling/createMessage`・`elicitation/create` は、サーバーが独立したリクエストとして送るのではなく、処理中のクライアントリクエストへの中間結果として返す形になります。原文でも「これは破壊的変更である」と明記されています。

具体的には、サーバーは `resultType: "input_required"` の `InputRequiredResult` を返し、その `inputRequests` に必要な要求をサーバー割り当ての識別子付きマップとして載せます。クライアントは入力を集めたうえで、元のリクエストを **新しい JSON-RPC ID** で再送し、`inputResponses` と、サーバーが付けていれば `requestState` をそのまま返します。`requestState` はサーバーだけが解釈する不透明な文字列で、クライアントは中身を検査・改変してはいけません。サーバー側は攻撃者に制御され得る入力として扱い、認可や業務ロジックに影響するなら HMAC や AEAD で完全性を保護し、リプレイ対策として認証済みプリンシパル・短い有効期限・元リクエストの識別子を含めることが推奨されます。この設計により、サーバーは共有ストレージやステートフルなロードバランシングなしに追加入力のやり取りを実現できます。

`InputRequiredResult` を返せるのは `prompts/get`・`resources/read`・`tools/call` の 3 つに限られます。またこの変更にあわせ、全ての result に `resultType` フィールドが必須化されました。通常の結果は `"complete"`、MRTR の中間結果は `"input_required"` です。`resultType` を持たない旧リビジョンのサーバーからの結果は `"complete"` とみなさなければなりません。

- [Multi Round-Trip Requests - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr#multi-round-trip-requests)
- [Overview - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/basic/index#resulttype)

## 4. 通知ストリームの一本化

サーバーからクライアントへの変更通知が `subscriptions/listen` という 1 つの長寿命リクエストに統合されました。Streamable HTTP の HTTP GET エンドポイントと、`resources/subscribe` / `resources/unsubscribe` RPC は廃止されています。

クライアントは `notifications` フィルタで受け取りたい種別（`toolsListChanged` / `promptsListChanged` / `resourcesListChanged` / `resourceSubscriptions`）を明示して購読を開き、サーバーは要求されていない種別の通知を送ってはいけません。サーバーは最初のメッセージとして `notifications/subscriptions/acknowledged` を返し、そこには実際に受理したフィルタの部分集合と、購読を識別する `io.modelcontextprotocol/subscriptionId` が入ります。以後この購読で流れる全メッセージが同じ ID を `_meta` に持つため、単一チャネルの stdio でも複数購読を多重化して区別できます。`notifications/progress` や `notifications/message` のようなリクエスト単位の通知は、従来どおり対応するリクエストの応答ストリーム側に流れます。

購読の終了はクライアント側のストリーム切断または `notifications/cancelled`、サーバー側からの切断、トランスポート断のいずれかで起こります。サーバーが自発的に終了する場合は空の結果を返してから閉じることが推奨され、これがあれば正常終了、無ければ予期しない切断としてクライアントは再接続を判断できます。あわせて、Streamable HTTP から SSE ストリームの再開・再送（`Last-Event-ID` ヘッダーと SSE イベント ID）が削除されました。応答ストリームが切れた場合、クライアントは新しいリクエスト ID で再発行する必要があります。

- [Subscriptions - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions#opening-a-stream)

## 5. 主要機能の非推奨化と Tasks の拡張への移出

機能ライフサイクル・非推奨方針（SEP-2596）の導入にあわせ、非推奨状態の機能を一覧する登録簿ページが新設されました。非推奨の機能は仕様に残るものの削除が予定されており、新規実装は採用すべきでないとされます。最短でも本リビジョン公開から 12 か月の猶予期間が設けられます。

今回非推奨になったのは Roots・Sampling・Logging（SEP-2577）と、OAuth 2.0 動的クライアント登録（DCR）です。移行先としては、Roots はツールパラメーター・リソース URI・サーバー設定でのディレクトリ受け渡し、Sampling は LLM プロバイダー API への直接統合、Logging は stdio なら `stderr`、それ以外は OpenTelemetry が示されています。DCR は Client ID Metadata Documents（CIMD）が推奨され、CIMD 非対応の認可サーバーとの後方互換のためにのみ残ります。既に非推奨と記述されていた HTTP+SSE トランスポートと `includeContext` の `"thisServer"` / `"allServers"` も、本方針の下で正式に Deprecated として分類し直されました。

実験的機能としてコアプロトコルに置かれていた Tasks は、公式拡張 `io.modelcontextprotocol/tasks` へ移されたうえで再設計されました（SEP-2663）。ブロッキングする `tasks/result` はポーリング方式の `tasks/get` に置き換えられ、クライアントから実行中のタスクへ入力を渡す `tasks/update` が追加されています。`tasks/list` は削除され、サーバーはリクエストごとの事前合意なしにタスクハンドルを返せるようになりました。

- [Deprecated Features - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/deprecated#deprecated)
- [Tasks - MCP Docs](https://modelcontextprotocol.io/extensions/tasks/overview#how-tasks-work)

## 1. Versioning and Compatibility

ハンドシェイクが無くなった後のバージョン交渉を定義する新設ページです。交渉のためのやり取りは存在せず、各リクエストが `_meta` の `io.modelcontextprotocol/protocolVersion` で自らのバージョンを宣言し、サーバーはリクエストごとに受理・拒否を判断します。拒否時は `UnsupportedProtocolVersionError`（`-32022`）を返し、`data.supported` に自分が対応するバージョンを列挙します。クライアントはそこから相互に対応するものを選んで再送します。

拡張の交渉についても本ページで扱われます。拡張は能力の `extensions` フィールドに識別子と設定オブジェクトのマップとして宣言し、識別子は `_meta` キーの命名規則（接頭辞必須）に従います。片方だけが対応している場合は、対応側がコア動作へ戻すか適切なエラーで拒否しなければなりません。

後半は旧リビジョンとの相互運用にあてられています。`_meta` でメタデータを運ぶリビジョン（`2026-07-28` 以降）を「modern」、`initialize` でセッションを張るリビジョン（`2025-11-25` 以前）を「legacy」、両対応の実装を「dual-era」と呼び分け、7 通りの組み合わせについて成否と挙動を表にまとめています。判定はトランスポートごとに異なり、stdio では `server/discover` によるプローブ、Streamable HTTP では `400 Bad Request` の本文検査でサーバーの世代を見分けます。世代の判定結果はサーバー単位の性質なのでキャッシュしてよい、という指針も示されています。

- [Versioning and Compatibility - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning#protocol-version-negotiation)

## 2. Discovery

新設された `server/discover` RPC の仕様ページです。サーバーはこの RPC の実装が必須で、クライアントは他のリクエストを送る前に対応バージョン・能力・識別情報を問い合わせられます。リクエストは標準の `_meta` 以外に本体パラメーターを持ちません。

結果には対応バージョンの一覧 `supportedVersions`、能力オブジェクト `capabilities`、LLM 向けの自然言語ガイダンス `instructions` が含まれ、サーバーの名前とバージョンは `_meta` の `io.modelcontextprotocol/serverInfo` に入ります。この結果はキャッシュ対象なので `ttlMs` と `cacheScope` も付きます。なお `serverInfo` はサーバーの自己申告でありプロトコルとして検証されないため、表示・ログ・デバッグ用途に限り、挙動の変更やセキュリティ判断に使うべきではないと注記されています。

呼び出しは任意である一方、有用な場面が 2 つ挙げられています。1 つは `tools/list` などを個別に叩かずにサーバーの全体像を 1 リクエストで得たい場合、もう 1 つは stdio での後方互換プローブです。stdio にはリクエストごとの HTTP ステータスコードが無いため、modern・legacy 双方に対応するクライアントはまず `server/discover` を送るべきとされています。

- [Discovery - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/server/discover#when-to-call)

## 3. Multi Round-Trip Requests

MRTR パターンの仕様ページです。冒頭に、サーバーから届く `roots/list`・`sampling/createMessage`・`elicitation/create` は必ず本パターンで送らなければならず、従来のサーバー起点リクエストはもはやサポートされない破壊的変更である旨の注記が置かれています。

型としては、サーバー割り当ての識別子をキーにリクエストを並べる `InputRequests`、同じキーでクライアントの結果を返す `InputResponses`、そしてこの 2 つと不透明な `requestState` を運ぶ `InputRequiredResult` が定義されます。サーバー要件としては、クライアントが能力宣言していない種別の要求を含めないこと、`inputRequests` と `requestState` の少なくとも一方を必ず含めること、クライアントが必ず応じるとは仮定しないことなどが挙げられています。クライアント要件としては、`requestState` をそのまま反映して返すこと、再送では初回と異なる JSON-RPC ID を使うことが定められています。

エラー処理では、クライアントが要求された情報を返しきれていない場合、サーバーはエラーではなく不足分を求める新しい `InputRequiredResult` を返すべきとされています。

- [Multi Round-Trip Requests - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr#core-types)

## 4. Subscriptions

`subscriptions/listen` の仕様ページです。通常のリクエストと違いストリームは開いたままになり、クライアントがキャンセルするまで通知を配信し続けます。`resources/subscribe` RPC と HTTP GET エンドポイントを置き換えるものです。

購読フィルタは 4 種類で、`toolsListChanged` / `promptsListChanged` / `resourcesListChanged` の真偽値と、監視したいリソース URI の配列 `resourceSubscriptions` です。いずれも任意で、省略はその種別を購読しないことを意味します。確認応答 `notifications/subscriptions/acknowledged` には、サーバーが実際に受理したフィルタの部分集合が入るため、クライアントは要求との差分を確認して未対応の種別を穏当に扱うべきとされています。

購読 ID は `subscriptions/listen` リクエストの JSON-RPC ID がそのまま使われ、ストリーム上の全メッセージの `_meta` に付きます。複数購読を同時に開くこともでき、stdio のように全メッセージが 1 チャネルを共有する環境ではこの ID で対応付けます。stdio では接続が切れて張り直された場合、サーバーは購読状態を保持しないためクライアントが再送する必要があります。

- [Subscriptions - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions#notification-filter)

## 5. Caching

結果キャッシュの仕様を定めた新設ページです。`server/discover`・`tools/list`・`prompts/list`・`resources/list`・`resources/templates/list`・`resources/read` の各操作は、`resultType: "complete"` の結果にキャッシュヒントを必ず含めなければなりません。`"input_required"` の中間結果はキャッシュ対象外です。

ヒントは 2 つのフィールドで表されます。`ttlMs` は結果を新鮮とみなしてよいミリ秒数で、HTTP の `Cache-Control: max-age` に相当します。`0` は即座に陳腐化、負値は無視して `0` 扱い、欠落時も `0` とみなします。`cacheScope` は `"public"` か `"private"` で、前者はユーザー固有データを含まず共有プロキシが誰にでも返してよいこと、後者は同一の認可コンテキスト内でのみ再利用できることを意味します。TTL はあくまで新鮮さのヒントであってデータ不変の保証ではなく、ポーリング間隔として使うべきではない旨が明記されています。

変更通知との関係は補完的で、通知が届いた時点でキャッシュは即座に陳腐化します。ページネーションとの関係では、各ページが独立したキャッシュ単位となり、ページごとに異なる `ttlMs` を返してもよい一方、同一リスト要求の全ページには同じ `cacheScope` を適用しなければなりません。セキュリティ上の注意として、認証済みエンドポイントの結果でも `"public"` を付けると認可コンテキストを越えて共有され得るため、`cacheScope` だけに依存せずプリミティブ単位のアクセス制御を行うべきとされています。

- [Caching - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching#cacheable-model)

## 15. Client Registration

クライアント登録の方式を独立させたページです。Client ID Metadata Documents（CIMD）、事前登録、動的クライアント登録（DCR）の 3 つを挙げ、すべてに対応するクライアントは「事前登録済み情報 → CIMD → DCR → 利用者への手入力依頼」の順で選ぶべきとしています。

CIMD は、HTTPS URL をクライアント識別子として使い、その URL が指す JSON 文書にクライアントのメタデータを置く方式です。クライアントと認可サーバーに事前の関係が無いという MCP でよくある状況に対応するもので、`client_id` は https スキームかつパス要素を持つ URL でなければならず、文書内の `client_id` は URL と完全一致する必要があります。認可サーバー側には、取得した文書の `client_id` と URL の一致確認、リダイレクト URI の照合、HTTP キャッシュヘッダーを尊重したキャッシュなどが求められます。対応の告知は認可サーバーメタデータの `client_id_metadata_document_supported` で行います。DCR は本リビジョンで非推奨となり、CIMD 非対応の認可サーバーとの後方互換のためにのみ残されました。

- [Client Registration - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration#client-id-metadata-documents)

TypeScript スキーマから生成されるスキーマ参照ページが、新リビジョンの内容に置き換わりました。今回の差分では最大規模のページで、`InputRequiredResult`・`InputRequests`・`InputResponses`・`DiscoverResult`・`CacheableResult`・`UnsupportedProtocolVersionError`・`MissingRequiredClientCapabilityError`・`HeaderMismatchError` といった新しい型が加わる一方、`initialize` まわりやタスク関連の型が姿を消しています。あわせて、生成器のオプション指定に起因して `minimum` / `maximum` / `default` が整数型として出力されていた問題が修正され、`schema.json` が TypeScript 定義どおり数値型を反映するようになりました。

- [Schema Reference - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/schema)

## 4. Tools

ツール仕様のページです。`tools/call` に対して `InputRequiredResult` を返す方法を説明する節が新設され、サーバーが追加入力を求める応答と、クライアントが `inputResponses` と `requestState` を添えて再送する例が示されました。一覧通知の節も、`subscriptions/listen` で `toolsListChanged` を要求したクライアントに対して送る、という記述に改められています。

能力の説明には、`tools/list` が返す集合は接続ごとに変わってはならない一方、リクエストに提示された認可によって変わることは認められる、という要件が加わりました。資格情報は接続状態ではなくリクエスト入力だから、という理由付きです。加えて、クライアント側のキャッシュと LLM のプロンプトキャッシュのヒット率を上げるため、ツールを決定的な順序で返すことが推奨されています。

データ型では、Tasks のコアからの移出に伴って `execution.taskSupport` が削除されました。代わりに、ツールパラメーターを HTTP ヘッダーへ写す `x-mcp-header` 注釈が追加されています。ツール名については、一意性の保証はサーバー単位であり、複数サーバーのツールを集約するクライアントやプロキシは衝突に備えて接頭辞などの区別策を実装すべきこと、`serverInfo` の名前は一意とは限らないので区別に使うべきでないことが注記されました。

- [Tools - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#input-required-tool-results)

## 5. Resources

リソース仕様のページです。`subscribe` 能力の説明が、`subscriptions/listen` の `resourceSubscriptions` フィルタ経由で個別リソースの更新通知に対応するかどうか、という意味に改められました。`listChanged` と `subscribe` は独立に宣言でき、どちらも無ければ省略できる、という整理も加わっています。

Tools と同様に、`resources/list` が返す集合は接続ごとに変わってはならず、リクエストの認可による出し分けのみ認められるという要件が追加されました。一覧・読み取りの結果には `resultType` とキャッシュヒント（`ttlMs` / `cacheScope`）が入り、`resources/list` がページネーションに加えてキャッシュにも対応することが明記されています。

- [Resources - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/server/resources#capabilities)

## 6. Prompts

プロンプト仕様のページです。リクエスト例から `_meta` を省略している旨の注記が加わり、`prompts/list` がキャッシュに対応することと、結果に `resultType` とキャッシュヒントが入ることが反映されました。一覧変更通知も、購読ストリームで `promptsListChanged` を要求したクライアントへ送る形に改められています。

- [Prompts - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/server/prompts#listing-prompts)

## 7. Logging

ログ機能のページ冒頭に非推奨の警告が置かれました。本リビジョンから最低 12 か月は仕様に残るものの、新規実装は採用すべきでなく、既存実装は stdio なら `stderr`、構造化された可観測性が必要なら OpenTelemetry へ移行すべきとされています。

仕組み自体も変わりました。`logging/setLevel` リクエストが削除され、ログを受け取りたいクライアントはリクエストの `_meta` に `io.modelcontextprotocol/logLevel` を入れる方式になっています。このフィールドを含まないリクエストに対して、サーバーは `notifications/message` を送ってはいけません。通知はリクエストスコープであり、当該リクエストの応答ストリーム上でのみ配信され、`subscriptions/listen` のストリームに流してはならないことも明記されました。

- [Logging - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/logging#per-request-log-level)

## 8. Sampling

サンプリング仕様のページ冒頭に非推奨の警告が置かれ、新規実装は LLM プロバイダーの API に直接統合すべきとされました。能力宣言はリクエストごとの `_meta.io.modelcontextprotocol/clientCapabilities` に置く形に改められ、例もそれにあわせて書き直されています。

`sampling/createMessage` は独立したリクエストではなく、`InputRequiredResult` の `inputRequests` に入れて返すものになりました。クライアントの結果も、元のリクエストを再送する際の `inputResponses` として返します。「Tools in Sampling」の節には、`tools` 配列に載せるツール定義はそのサンプリングリクエストにスコープされ、サーバーが公開している登録済みツールと対応している必要はない、という説明が加わりました。`includeContext` の `"thisServer"` / `"allServers"` は「ソフト非推奨」から正式な Deprecated に格上げされ、Sampling 本体より後に削除されることはないと明記されています。

- [Sampling - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/client/sampling#tools-in-sampling)

## 9. Elicitation

ユーザーへの入力要求も MRTR 経由に改められました。能力宣言はリクエストごとの `_meta` に置く形になり、リクエスト例・応答例はいずれも `InputRequiredResult.inputRequests` の中身と `inputResponses` に返す値という形式で示されています。

`2025-11-25` で導入された `notifications/elicitation/complete` 通知と、URL モード elicitation の `elicitationId` フィールドは削除されました。MRTR では、クライアントは元のリクエストを再送することで帯域外のやり取りの結果を知るため、サーバー起点の完了通知とそれを対応付ける識別子が構造上不要になったためです。再送をまたいで elicitation を対応付けたいサーバーは、自前の識別子を `requestState` に埋め込むことになります。フォームモードのスキーマ例からは `pattern` の指定が外れました。

- [Elicitation - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation#elicitation-requests)

## 10. Roots

Roots のページ冒頭にも非推奨の警告が置かれ、新規実装はディレクトリやファイルをツールパラメーター・リソース URI・サーバー設定で渡すべきとされました。あわせて、Roots は「関連するディレクトリやファイルをサーバーに伝える情報提供」であってアクセス制御の仕組みではなく、サーバーが roots の外に出ないことをプロトコルが強制するわけではない、という位置づけが明示されています。

`listChanged` 能力と `roots/list_changed` 通知は削除されました。roots の一覧が変わってもクライアントから通知は飛ばず、サーバーは次に `roots/list` を要求したときに新しい境界を知ることになります。`roots/list` 自体も MRTR 経由の受け渡しに変わっています。

- [Roots - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/client/roots#capabilities)

## 11. Architecture

仕様側のアーキテクチャページです。冒頭の説明から「ステートフルなセッションプロトコル」という記述が消え、すべてのリクエストが自己完結し自らのプロトコルバージョンと能力を運ぶステートレスなプロトコルである、と書き換えられました。クライアントの説明も「サーバーごとにステートフルなセッションを 1 つ確立する」から「厳密に 1 つのサーバーと通信し、全リクエストにプロトコルバージョンと能力を付与する」に変わっています。

能力交渉の節も、初期化時に宣言する形から、クライアントは各リクエストの `_meta` で、サーバーは `server/discover` の応答で宣言する形に改められました。シーケンス図も更新され、初期化のやり取りが任意の探索ステップになり、サーバーがクライアント入力を必要とする場合の `InputRequiredResult` と再送のループが描かれています。

- [Architecture - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/architecture/index#capability-negotiation)

## 12. Architecture overview

学習ガイド側のアーキテクチャ解説です。データレイヤーの構成要素から「ライフサイクル管理」が消えて「探索」に置き換わり、「ステートレス性と探索」という節が新設されました。クライアント機能の説明では Sampling と Logging が非推奨として区別され、Elicitation が MRTR パターンで配信されることが明記されています。Tasks は横断的なユーティリティプリミティブではなく拡張として紹介されるようになりました。

後半のウォークスルーは大きく書き換わっています。`initialize` リクエスト・レスポンスの例が `server/discover` の例に差し替えられ、`notifications/initialized` の送信ステップが削除されました。`tools/list` の例にも `_meta` が付き、結果に `resultType` と `ttlMs` / `cacheScope` が入る形に更新されています。Python SDK の擬似コードも `ClientSession` を使う形から `Client` を使う形に置き換わり、探索は接続時に行われて結果はクライアントオブジェクトから参照できる、という説明が添えられました。

- [Architecture overview - MCP Docs](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture#statelessness-and-discovery)

## 13. Understanding MCP clients

クライアント機能の解説ページです。冒頭の一覧表で Roots と Sampling に非推奨である旨が併記され、それぞれの節にも警告と移行先が置かれました。Roots の説明からは `roots/list_changed` による通知の記述が消え、サーバーは次回の `roots/list` で新しい境界を知る、という形に改められています。

Elicitation の節は加筆されました。フォームモードと URL モードの 2 つがあること、URL モードは帯域外でやり取りが行われるため資格情報の入力や第三者 OAuth のような機微な用途に向くこと、そして MRTR パターンで配信されることが説明されています。プライバシーの記述も、パスワードや API キーなどの機微情報はフォームモードで要求してはならず URL モードで扱うべき、という具体的な指針に置き換わりました。Sampling の節には、サンプリング中にツール使用を要求できること、そのツール定義はサーバーが公開するツールと対応している必要はないことが追記されています。

- [Understanding MCP clients - MCP Docs](https://modelcontextprotocol.io/docs/2026-07-28/learn/client-concepts#elicitation)

## 14. Build an MCP client

クライアント構築チュートリアルです。Python タブは前提条件に「Python MCP SDK 2.0.0 以上を使う必要がある」が加わり、実装も全面的に書き直されました。`ClientSession` と `AsyncExitStack` を抱える `MCPClient` クラスが廃され、`Client` オブジェクトを `async with` で開いて接続のライフサイクル全体を任せる形になっています。ツール一覧の取得は `client.list_tools()`、スキーマの参照は `tool.inputSchema` から `tool.input_schema` に変わりました。ツール結果は `CallToolResult` で、`content` はブロックのリストなので `TextContent` に絞ってから `.text` を読む例が示され、失敗したツールは例外を投げずに `is_error` を立てて返るため、そのフラグをそのまま Claude に渡す方針が説明されています。対話ループでは `input()` を `asyncio.to_thread` 経由で呼び、イベントループを塞がないようにしています。使用モデルは `claude-opus-5` に更新され、タイムアウト時の対処も `Client` の `read_timeout_seconds` を上げる案内に変わりました。

TypeScript タブは、必要な Node.js が 17 以上から 20 以上に引き上げられ、依存パッケージが `@modelcontextprotocol/sdk` から `@modelcontextprotocol/client` に変わりました。インポートパスもそれにあわせて変更され、`tsconfig.json` に `"types": ["node"]` が追加されています。ツール結果をメッセージへ渡す箇所は、文字列としてキャストしていたのをテキストブロックだけ抽出して連結する形に直されました。Java タブでは、クライアントのカスタマイズが `McpClientCustomizer` を型引数付きで使う形になり、対応トランスポートの記述が SSE から Streamable HTTP に変わって接続 URL の設定例が追加されています。WebFlux スターターの成果物 ID も新しい命名に更新されました。

- [Build an MCP client - MCP Docs](https://modelcontextprotocol.io/docs/2026-07-28/develop/build-client)

## 15. Build an MCP server

サーバー構築チュートリアルです。Python の前提が SDK 1.2.0 以上から 2.0.0 以上に引き上げられ、サーバークラスが `FastMCP` から `MCPServer` に変わりました。依存関係のインストールも `uv add "mcp[cli]" httpx` から `uv add "mcp[cli]"` に簡略化され、HTTP クライアントは SDK 自身が依存する `httpx2` を使う形になっています。エントリポイントも `main()` 関数を挟まず `if __name__ == "__main__":` で直接 `mcp.run(transport="stdio")` を呼ぶ形に整理されました。

ロギングの注意書きも書き換わりました。stdio サーバーでは `print()` を `file=sys.stderr` 付きで使うという案内が消え、`print()` は stdio サーバーから完全に排除し、標準ライブラリの `logging` をモジュールごとの `logging.getLogger(__name__)` で使うことが推奨されています。

## 16. Debugging

デバッグガイドです。サーバー側ログの推奨手段が `notifications/message` から stderr と OpenTelemetry に改められ、プロトコル経由のロギングが非推奨である旨の警告が加わりました。Python のサンプルも `ctx.session.send_log_message()` を呼ぶものから、標準の `logging` を使うものに差し替えられています。ログレベルの調整も `logging/setLevel` ではなく、リクエストの `_meta` に `io.modelcontextprotocol/logLevel` を入れる方式として説明されるようになりました。

Streamable HTTP のデバッグ手順からは `Mcp-Session-Id` ヘッダーの確認が消えました。「サーバーの初期化」という節は「サーバーの起動」に改称され、接続問題の切り分け手順も、`server/discover` で対応バージョンを確認し、`UnsupportedProtocolVersionError`（`-32022`）の `data` から対応バージョンを読む、という流れに置き換わっています。

## 17. Understanding Authorization in MCP

認可チュートリアルの Python 実装例が更新されました。サーバークラスが `FastMCP` から `MCPServer` に置き換わり、外部の FastMCP プロジェクトへの参照ではなく Python SDK のドキュメントを指す説明に改められています。`MCPServer` が保護対象リソースメタデータ文書を公開し、未認証リクエストにはその文書を指す `WWW-Authenticate` ヘッダー付きの `401` を返し、ベアラートークンを設定した検証器に渡す、という役割が明記されました。

設定クラス `config.py` も整理されました。`OAUTH_CLIENT_SECRET` の既定値がプレースホルダから空文字列になり、`OAUTH_STRICT` と `TRANSPORT` の項目、およびトランスポート値を検証する `validate()` メソッドが削除されています。サーバー生成側でも `host` / `port` / `streamable_http_path` の指定が不要になりました。

## 18. Security Best Practices

セキュリティのベストプラクティスです。プロトコルからセッションが無くなったことを受け、「セッションハイジャック」の節が「状態ハンドルハイジャック」の節に置き換わりました。サーバーが発行したカート ID やワークフロー ID のようなハンドルを第三者が入手・推測して他人の状態を読み書きする攻撃として整理され、緩和策も「ハンドルの所持を認証とみなしてはならない」「推測困難なハンドルを使う」という形に書き直されています。従来あった、複数のステートフル HTTP サーバー間でセッション ID を悪用するプロンプトインジェクションのシーケンス図は削除されました。

トークンパススルーの節には、他のリソース向けに発行されたトークンを受け入れることの危険性が「オーディエンス検証の失敗」と「トークンのパススルー」の 2 側面に分けて追記されました。SSRF の節には、認可サーバー自身が標的になる場合の説明が加わっています。CIMD に対応する認可サーバーは未知のクライアントから受け取った URL を取得しに行くため、悪意あるクライアントが任意の URL へのリクエストを誘発できるという指摘で、プライベート IP 帯の遮断や egress プロキシといった対策が同様に当てはまるとされています。

- [Security Best Practices - MCP Docs](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices#state-handle-hijacking)
