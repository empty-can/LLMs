## 1. 2025-11-25 以前のバージョンでの拡張の宣言方法が明文化された

今回の取り込みは 1 回で、差分は本文 `llms-full.txt` の追加 71 行・削除 6 行です。`llms-full.txt` の総行数は 45,410 行から 45,475 行になり、収録ページ数（158 件）は変わっていません。索引 `llms.txt` には変更がなく、エントリ数は 363 件のままです。追加行の大半（63 行）は Extensions Overview への追記で、残りは Extension Support Matrix（追加 2 行）と Tools（6 行の書き換え）です。

Extensions Overview の Negotiation は、これまで `2026-07-28` の仕組みだけを説明していました。クライアントは各リクエストの `_meta["io.modelcontextprotocol/clientCapabilities"]` で、サーバーは `server/discover` のレスポンスで、それぞれ `extensions` フィールドに対応する拡張を載せるというものです。今回、Negotiation の冒頭に「以下の例はプロトコルバージョン `2026-07-28` 以降のもので、`2025-11-25` 以前については Initialization-Based Versions を参照」という案内が入り、Server Capabilities の後ろ（Graceful Degradation の前）に「Initialization-Based Versions」の節が新設されました。

**新しい節の内容**: 拡張がプロトコルの正式な一部になったのはバージョン `2026-07-28` からですが、それ以前から多くの SDK・クライアント・サーバーが、`2025-11-25` 以前のバージョンで [`initialize` のハンドシェイク](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle#initialization)の中で拡張を交渉していました。その際はリクエストの `params.capabilities.extensions` とレスポンスの `result.capabilities.extensions` を使います。拡張の識別子と設定オブジェクトは、`2026-07-28` の場合と同じ規則に従います。

**注意書き（NOTE）**として、次の点が挙げられています。

- `extensions` フィールドは、これらのプロトコルバージョンの公開スキーマには含まれておらず、対応は適合性（conformance）の要件ではない
- `initialize` を通じて `capabilities.extensions` を受け渡せる SDK は、プロトコルバージョンをまたいで拡張が一貫して動くよう、そうすることが推奨される
- 利用する SDK がこのフィールドを送受信できるか、また拡張が交渉したプロトコルバージョンに対応しているかを確認する
- 相手側の capabilities に `extensions` が無い場合や、特定の拡張が含まれていない場合は、その拡張を未対応として扱い、Graceful Degradation に従う

節には、クライアントの `initialize` リクエスト（`protocolVersion` が `2025-11-25`、`capabilities` に `roots` と、`extensions` の中の `io.modelcontextprotocol/ui`（`mimeTypes: ["text/html;profile=mcp-app"]`））と、サーバーの `initialize` レスポンス（`capabilities` に `tools` と `extensions` の `io.modelcontextprotocol/ui`（空のオブジェクト））の JSON の例が付いています。

- [Extensions Overview - MCP Docs](https://modelcontextprotocol.io/extensions/overview#initialization-based-versions)

## 2. Extension Support Matrix に Claude Code と Kiro Crew が加わった

Extension Support Matrix は、どの MCP クライアントがどの公式拡張に対応しているかをまとめたページです。今回、Support matrix の表に 2 行が加わりました。

- **Claude Code**（`https://claude.com/claude-code` へのリンク）: Claude Desktop の次の 3 行目
- **Kiro Crew**（`https://kiro.dev/crew/` へのリンク）: PostHog Code の次、fast-agent の前

これで表に並ぶクライアントは 14 件から 16 件になりました。表のセルは、Skills 列にある 3 件の Partial のリンク（ChatGPT・fast-agent・MCP Inspector）を除いてすべて空で、追加された 2 行も 5 列すべてが空です。このため、Claude Code と Kiro Crew がどの拡張に対応しているかは `llms-full.txt` からは読み取れません。同じページの Extension overview の表（4 件）には変更がありません。

- [Extension Support Matrix - MCP Docs](https://modelcontextprotocol.io/extensions/client-matrix#support-matrix)

## 3. Tools の Embedded Resources の例で annotations の位置が直された

仕様（2026-07-28 版）の Tools ページの Embedded Resources の項には、`file:///project/src/main.rs` を埋め込んだ `"type": "resource"` のコンテンツブロックの JSON の例があります。これまでの例では、`annotations`（`audience`・`priority`・`lastModified`）が `resource` オブジェクトの内側に `uri`・`mimeType`・`text` と並んで置かれていました。今回、`annotations` が `resource` の外に出て、`type`・`resource` と同じ階層（コンテンツブロックの直下）に移りました。`annotations` の値そのものは変わっていません。

同じ版の Schema Reference では、`EmbeddedResource` が `type`・`resource`・`annotations`・`_meta` を持ち、`resource` に入る `TextResourceContents` / `BlobResourceContents` には `annotations` がありません。Schema Reference にある「Embedded file resource with annotations」の例も `annotations` をコンテンツブロックの直下に置いており、Tools ページの例がこれと揃ったことになります。例の直後にある、埋め込みリソースも通常のリソースと同じ Resource annotations に対応するという説明文は変わっていません。

- [Tools - MCP Docs](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#embedded-resources)

## 1. Extensions Overview
