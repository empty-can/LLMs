## 1. Python 例からハードコードされたクライアントシークレットを除去

「Understanding Authorization in MCP」の「Implementation Example」（Keycloak を認可サーバーとして動かす例）にある、Python 版の設定ファイル `config.py` の例が修正されました。`OAUTH_CLIENT_SECRET` の既定値には従来 `UO3rmozkFFkXr0QxPTkzZ0LMXDidIikB` という実際のシークレットに見える文字列が直書きされていましたが、これがプレースホルダ `<YOUR_SERVER_CLIENT_SECRET>` に置き換えられました。同ページの「Keycloak Setup」には「クライアント資格情報をコードに直接埋め込んではならない」という警告が既に置かれており、Python の例がその警告と食い違っていた状態が解消された形です。TypeScript タブの `.env` 例は以前からプレースホルダ表記だったため、タブ間の記述も揃いました。

あわせて `OAUTH_CLIENT_ID` の既定値が `mcp-server` から `test-client` に変更されています。こちらはプレースホルダ化ではなく具体値の差し替えで、同じページ内の他の記述（後述するイントロスペクションのコメントに現れる `aud` の例など）で使われているクライアント ID に揃えたものです。いずれも既定値の変更のみで、環境変数 `OAUTH_CLIENT_ID` / `OAUTH_CLIENT_SECRET` から読み込む仕組み自体は変わっていません。

- [Understanding Authorization in MCP - MCP Docs](https://modelcontextprotocol.io/docs/tutorials/security/authorization#mcp-server-setup)

## 2. トークンイントロスペクションがパブリッククライアントに対応

同じ Python 実装例の `IntrospectionTokenVerifier.verify_token` で、イントロスペクションエンドポイントへ送るフォームデータの組み立て方が変わりました。従来は `token` / `client_id` / `client_secret` の 3 つを常に含めていましたが、修正後は `token` と `client_id` のみを最初に組み立て、`self.client_secret` が設定されている場合にだけ `client_secret` を追加するようになっています。

追加されたコメントでは、パブリッククライアントは `client_id` のみで認証する旨が説明されています。従来のコードはシークレットを持たない構成でも空文字列の `client_secret` を送ってしまい、認可サーバーによってはこれが認証エラーの原因になり得ました。`config.py` 側の `OAUTH_CLIENT_SECRET` が空でも動作するようになったという点で、前掲のプレースホルダ化とも噛み合う変更です。

- [Understanding Authorization in MCP - MCP Docs](https://modelcontextprotocol.io/docs/tutorials/security/authorization#mcp-server-setup)

## 3. リスト形式の aud による silent 401 を修正

同じ `verify_token` の戻り値を組み立てる箇所で、`AccessToken` の `resource` フィールドに渡す値が `data.get("aud")`（イントロスペクション応答の `aud` クレームそのもの）から `self.resource_url`（サーバー自身のリソース URL）に変更されました。

追加された長いコメントが理由を説明しています。`AccessToken.resource` の型は `str | None` である一方、Keycloak はここで `aud` を `["test-client", "http://localhost:3000", "account"]` のような**リスト**で返すことがあり、それをそのまま渡すと pydantic が `ValidationError` を送出します。この例外は直後の広い `except Exception` に捕まって `None` を返すため、呼び出し側からは理由の分からない 401 に見えてしまう、というのが従来の挙動でした。修正では、直前の `_validate_resource` でこのサーバーのリソースが有効な audience に含まれることを既に確認している点を根拠に、確認済みの `self.resource_url` を記録するようにしています。`_validate_resource` / `_is_valid_resource` 側のロジック（`aud` が文字列・リストのいずれの形式でも扱い、1 つでも一致すれば受理する）に変更はありません。

- [Understanding Authorization in MCP - MCP Docs](https://modelcontextprotocol.io/docs/tutorials/security/authorization#mcp-server-setup)

## 4. Python サーバーのパッケージ構成と起動手順を追加

Python タブの末尾に「Python MCP Server」と題した節が新設されました。サーバーのルートに `pyproject.toml` と `mcp_server` フォルダーを置き、Python ファイルはすべて `mcp_server` フォルダーに入れる、というファイル配置の指針が示されています。

続けて `pyproject.toml` の記述例が全文で掲載されました。プロジェクト名 `mcp-simple-auth`、`requires-python = ">=3.10"`、依存関係（`anyio` / `click` / `httpx` / `mcp` / `pydantic` / `pydantic-settings` / `sse-starlette` / `uvicorn`）、エントリポイント `mcp-simple-auth-rs = "mcp_server.server:main"`、ビルドバックエンドとしての `hatchling`、開発用依存グループ（`pyright` / `pytest` / `ruff`）が含まれます。最後に、`uv sync` で依存を同期し、`uv run mcp-simple-auth-rs --port=3000 --auth-server=http://localhost:8080 --transport=streamable-http` でサーバーを起動するコマンドが示されました。ページ本文の案内も「詳細は Python SDK のドキュメントを参照」から「以下、または Python SDK のドキュメントを参照」に改められ、この節へ誘導する形になっています。

- [Understanding Authorization in MCP - MCP Docs](https://modelcontextprotocol.io/docs/tutorials/security/authorization#mcp-server-setup)
