# Phase2 検討: テキストマイニングによる名詞のカテゴリ適性スコアリング

作成日: 2026-07-12 ／ 入力: `official-llms-txts/code.claude.com/docs/llms-full.txt`（165 ページ、whats-new 除外後 148 ページ）
プロトタイプ: `work/categorize-algorithm/scripts/term_scoring.py` ／ 実行結果: `output/term-scores.md`

---

## 0. 結論（先に要点）

**成立する。** llms-full.txt を入力に、出現頻度・文書横断性・共起関係を組み合わせた統計スコアリングで、「環境変数」「コマンド」のような**見出し横断型のカテゴリ候補語**を上位に集められることを実データで確認した（プロトタイプ実装・実行済み）。

ただし品詞情報なしの純統計では一般語の混入が残るため、推奨構成は**全自動でのカテゴリ確定ではなく半自動**:

> スコアリング（機械）→ 上位語＋クラスタ素案を人が一度レビューして taxonomy 確定（人手/LLM 補助）→ 日次サマリ生成はその語彙表で分類（機械＋LLM）

これはメンバープロファイル不要・チャットルーム一斉通知と両立し、taxonomy の鮮度維持（docs 大改編時の再計算）も機械側でできる。

---

## 1. 手法サーベイと「カテゴリ適性」への適合性

| 手法 | 測るもの | カテゴリ適性への適合 |
|---|---|---|
| **TF-IDF** | ある文書に特有な語 | **そのままでは逆選択**。IDF は「少数文書にしか出ない語」を持ち上げるが、カテゴリ語は逆に「多くのページを横断する語」。ただし「全ページ遍在の汎用語を落とす」目的では部分的に有効 |
| **RAKE** | ストップワード区切りの句を候補化＋共起次数/頻度 | 候補句の**切り出し器として優秀**（品詞タガー不要）。スコア自体は文書単位向け |
| **YAKE** | 大文字・位置・文脈多様性等の教師なし特徴 | 単一文書のキーワード向け。コーパス横断評価には設計拡張が必要 |
| **C-value / NC-value** | 句の termhood（より長い句に包含される出現の割引） | **有効**。「mcp server」を「server」と別語として正しく立てる。複合語が多い技術文書と相性が良い |
| **TextRank / 共起グラフ中心性** | 共起ネットワーク上のハブ性 | **有効**。多くの語と共起する語＝多くの話題に接続する概念で、まさにカテゴリ適性 |
| **PMI / NPMI** | 語と語の共起の偶然超過 | 語のグルーピング（クラスタ化）に有効。カテゴリ**候補の周辺語彙**（同義・下位概念）の同定に使える |
| **分散度指標（Gries DP / Juilland D）** | コーパス全体への出現の均一性 | **有効**。特定ページに偏る語（ページ固有語）と横断語を弁別する |
| **LDA 等トピックモデル** | 文書集合の潜在トピック | カテゴリ数を与えれば taxonomy 素案を直接出せるが、要外部ライブラリ・結果の解釈/再現の安定性に難 |
| **埋め込み系（KeyBERT 等）** | 意味ベクトル類似 | 品質は高いがモデル・依存が重い。本リポジトリの「LLM 判断は claude -p、他は素のスクリプト」という設計に合わない |

**設計上の核心**: 一般的なキーワード抽出は「その文書らしさ」を探すが、今回欲しいのは「**どの文書にも属さず、複数の文書を束ねる語**」。したがって特化度（TF-IDF 的な軸）を*ペナルティ*側に使い、横断性・共起ハブ性を*報酬*側に使う、通常と逆向きの合成が必要になる。

## 2. プロトタイプの設計

環境制約（Python 3.14・外部パッケージなし）を踏まえ、上記から純 Python で実装可能な 4 指標を選んで合成した。

```
score(t) = ( C-value(t) × band(coverage(t)) × evenness(t) × centrality(t) )^(1/4) × heading_bonus(t)
```

| 指標 | 実装 | 狙い |
|---|---|---|
| **C-value**（termhood） | 長い候補句に包含される出現を割引 | 「本当に句として立つ語」の選別。mcp server ⊂ server の分離 |
| **band**（被覆バンドパス） | ページ被覆率 30% をピークとする対数正規カーブ | 少数ページ特化語（≒ページ固有語）と全ページ遍在語（≒弁別力ゼロ）の両方を落とす |
| **evenness**（分散均一度） | 1 − Gries DP | 高頻度でも一部ページに偏在する語を落とす |
| **centrality**（共起ハブ性） | ページ共起 NPMI>0.1 の相手数（正規化） | 多話題に接続する概念を持ち上げる |
| **heading_bonus** | 複数ページの h2〜h4 見出しに出る語に最大 +64% | 「見出しを横断する概念」という作業指示の着眼を直接反映 |

候補句の切り出しは RAKE 流（ストップワード/句読点区切り、1〜4 語）で品詞タガーを回避。複数形は単数形が語彙にある場合のみ併合。**whats-new/（changelog 転載）ページは語彙抽出から除外**（「Fixed」等の更新動詞が統計を汚染するため。除外前は "fixed" が 73 位に混入していた→除外で消滅）。カテゴリ素案クラスタは h2 セクションを窓とした NPMI 共起の貪欲平均リンク法（ページ窓では横断語同士がほぼ全共起して 1 塊に潰れるため、窓を狭めた）。

### 3.2 カテゴリ素案クラスタ（上位 60 語・セクション NPMI 共起）

機械出力のまま（ラベルは筆者が括弧で付記）:

2. **hook** — subagent, window, rule, bash, context, task, conversation, resume, tool, behavior（→ エージェント実行・自動化）
3. **mode** — background, git, permission, shell, edit, script, worktree, status, input, command（→ 実行制御・パーミッション）
4. **settings** — json, managed, managed settings, project, block, source（→ 設定・管理）
5. **environment variable** — path, field, error, output, message, response, limit（→ 環境・入出力）
6. **model** — token（→ モデル・トークン）

人手ゼロの統計だけで、Phase1 で slug から手作業推定した領域（SDK/MCP/エンタープライズ/コア設定…）に近い構造が再現された。

## 4. 考察

**うまくいったこと**
- 検証語 12 個中 8 個が上位 60 位以内。特に作業指示で例示された「環境変数」（見出し横断概念）が 12 位に入り、**「見出し粒度では取れない横断カテゴリを語の統計で拾う」という狙いは実証できた**
- C-value の効果で「mcp server」「managed settings」「permission mode」「context window」等の複合概念語が単語と別に立った
- クラスタが taxonomy 素案としてそのまま議論の土台になる品質

**限界と対処**
1. **一般語の混入**（window, directory, field, key 等が上位に残る）: 品詞情報が無いため。対処: (a) 数十語のドメイン汎用語リスト追加（安価・即効）、(b) 最終確定を人/LLM レビューに置く半自動構成（推奨）
2. **遍在語の扱い**（command 51 位, session 176 位）: 被覆バンドのピーク（現行 30%）が「カテゴリ粒度」を決めるノブになっている。「session や command をカテゴリに欲しい」ならピークを 50〜60% に上げるか、遍在語だけ別枠（「コア/全般」カテゴリ）で拾う。**ここは統計でなくカテゴリ設計の意思決定**
3. **希少特化語**（slash command, checkpoint）: カテゴリではなくカテゴリ内トピックの粒度。上位語クラスタの「周辺語彙」として NPMI で紐付ければ、分類時のマッチング語彙（同義語表）に活用できる
4. **言語**: 抽出は en 語彙。ja カテゴリ名への写像（environment variable→環境変数）は taxonomy 確定時に一度だけ人手で付ければよい

## 5. 運用への組み込み案（Phase3 のたたき台）

```
[不定期・docs大改編時]                          [日次]
llms-full.txt ─→ term_scoring.py ─→ 候補ランキング   サマリ生成(claude -p)
                                      ＋クラスタ素案         │
                                          │                 │ categories.yaml の語彙で
                                    人手レビュー(1回)  ←──── 各変更項目を分類
                                          │                 │
                                    categories.yaml    タグ/グルーピング付きサマリ
                                （カテゴリ名 ja/en＋           │
                                  代表語＋周辺語彙）      チャットルーム通知
```

- **taxonomy 構築**: スコア上位 N ＋クラスタを人がレビューし、8〜12 カテゴリと各カテゴリの語彙（代表語＋NPMI 上位の周辺語）を `categories.yaml` に確定。ここだけ人手（1 回＋大改編時）
- **日次分類**: 変更項目のテキスト・対象 slug を categories.yaml の語彙とマッチング（機械）し、曖昧なもののみ生成時の LLM が判定。Phase1 の B1（インラインタグ）/B2（frontmatter メタ）/A1（グルーピング）のいずれの出力形態にもこの分類結果を流せる
- メンバープロファイル不要。「語彙表のメンテ」も統計スコアの再計算が起点なので、業務の移り変わりはメンバー側がカテゴリを見る目線を変えるだけで吸収できる

## 6. Phase2 で決めたい残論点

1. 遍在語の扱い（command/session を独立カテゴリにするか「コア/全般」に束ねるか）＝バンドピークの設定
2. カテゴリ数の目安（クラスタ素案は 6〜7 個＋小クラスタ。8〜12 を推奨）
3. taxonomy 確定レビューを人手のみでやるか、LLM（claude -p）に候補整形させて人が承認するか
4. スコア再計算のトリガー（定期 or docs 大改編検知 or 手動）
5. 分類結果を載せる出力形態（Phase1 の A1/A2/B1/B2 のどれと組むか）
