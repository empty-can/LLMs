# Phase2 検討: テキストマイニングによる名詞のカテゴリ適性スコアリング

作成日: 2026-07-12（v2: ページ名・見出しの規定加算を統合） ／ 入力: `official-llms-txts/code.claude.com/docs/llms-full.txt`（165 ページ、whats-new 除外後 148 ページ）
プロトタイプ: `work/categorize-algorithm/scripts/term_scoring.py` ／ 実行結果: `output/term-scores.md`

## 0. 結論（先に要点）

**成立する。** llms-full.txt を入力に、出現頻度・文書横断性・共起関係を組み合わせた統計スコアリングで、「環境変数」「コマンド」のような**見出し横断型のカテゴリ候補語**を上位に集められることを実データで確認した（プロトタイプ実装・実行済み）。さらに v2 で**ページ名（h1/slug）・ページ内見出し（h2〜h4）に含まれる語への規定加算**（作業指示者提案）を統合し、遍在語（session, command 等）がバンドパスで沈む問題が解消、クラスタ素案も 7 → 19 個へ細分化された。

ただし品詞情報なしの純統計では一般語の混入が残るため、推奨構成は**全自動でのカテゴリ確定ではなく半自動**:

> スコアリング（機械）→ 上位語＋クラスタ素案を人が一度レビューして taxonomy 確定（人手/LLM 補助）→ 日次サマリ生成はその語彙表で分類（機械＋LLM）

これはメンバープロファイル不要・チャットルーム一斉通知と両立し、taxonomy の鮮度維持（docs 大改編時の再計算）も機械側でできる。

## 1. 手法サーベイと「カテゴリ適性」への適合性

| 手法 | 測るもの | カテゴリ適性への適合 |
|---|---|---|
| **TF-IDF** | ある文書に特有な語 | **そのままでは逆選択**。IDF は「少数文書にしか出ない語」を持ち上げるが、カテゴリ語は逆に「多くのページを横断する語」。ただし「全ページ遍在の汎用語を落とす」目的では部分的に有効 |
| **RAKE** | ストップワード区切りの句を候補化＋共起次数/頻度 | 候補句の**切り出し器として優秀**（品詞タガー不要）。スコア自体は文書単位向け |
| **YAKE** | 大文字・位置・文脈多様性等の教師なし特徴 | 単一文書のキーワード向け。コーパス横断評価には設計拡張が必要 |
| **C-value / NC-value** | 句の termhood（より長い句に包含される出現の割引） | **有効**。「mcp server」を「server」と別語として正しく立てる。複合語が多い技術文書と相性が良い |
| **TextRank / 共起グラフ中心性** | 共起ネットワーク上のハブ性 | **有効**。多くの語と共起する語＝多くの話題に接続する概念で、まさにカテゴリ適性 |
| **PMI / NPMI** | 語と語の共起の偶然超過 | 語のグルーピング（クラスタ化）に有効。カテゴリ**候補の周辺語彙**（同義・下位概念）の同定に使える |
| **分散度指標（Gries DP / Juilland D）** | コーパス全体への出現の均一性 | **有効**。特定ページに偏る語（ページ固有語）と横断語を弁別する |
| **LDA 等トピックモデル** | 文書集合の潜在トピック | カテゴリ数を与えれば taxonomy 素案を直接出せるが、要外部ライブラリ・結果の解釈/再現の安定性に難 |
| **埋め込み系（KeyBERT 等）** | 意味ベクトル類似 | 品質は高いがモデル・依存が重い。本リポジトリの「LLM 判断は claude -p、他は素のスクリプト」という設計に合わない |

**設計上の核心**: 一般的なキーワード抽出は「その文書らしさ」を探すが、今回欲しいのは「**どの文書にも属さず、複数の文書を束ねる語**」。したがって特化度（TF-IDF 的な軸）を*ペナルティ*側に使い、横断性・共起ハブ性を*報酬*側に使う、通常と逆向きの合成が必要になる。

## 2. プロトタイプの設計（v2）

環境制約（Python 3.14・外部パッケージなし）を踏まえ、純 Python で実装可能な 4 統計指標の幾何平均に、**構造シグナル（ページ名・見出し）の規定加算**を組み合わせた。

```
score(t) = ( C-value(t) × band(coverage(t)) × evenness(t) × centrality(t) )^(1/4)
           + 0.25 × min(ページ名出現ページ数, 3)/3        ← ページ名（h1/slug）加算
           + 0.12 × min(見出し出現ページ数, 10)/10        ← ページ内見出し（h2〜h4）加算
```

| 成分 | 実装 | 狙い |
|---|---|---|
| **C-value**（termhood） | 長い候補句に包含される出現を割引 | 「本当に句として立つ語」の選別。mcp server ⊂ server の分離 |
| **band**（被覆バンドパス） | ページ被覆率 30% をピークとする対数正規カーブ | 少数ページ特化語（≒ページ固有語）と全ページ遍在語（≒弁別力ゼロ）の両方を落とす |
| **evenness**（分散均一度） | 1 − Gries DP | 高頻度でも一部ページに偏在する語を落とす |
| **centrality**（共起ハブ性） | ページ共起 NPMI>0.1 の相手数（正規化） | 多話題に接続する概念を持ち上げる |
| **ページ名加算** | h1 タイトルと slug のトークンに一致する語へ規定値を加算（複数ページ分で増額、3 ページで満額 +0.25） | **ページ名はカテゴリの最有力候補**という前提の直接反映（v2・作業指示者提案） |
| **見出し加算** | h2〜h4 見出しに出る語へ規定値を加算（10 ページ分で満額 +0.12） | 見出しを横断する概念の持ち上げ |

**加算（additive）にした理由**: 幾何平均への乗算ボーナスだと、統計軸が 1 つでも弱い語（例: 被覆率が低いページ名語）は結局沈んだままになる。加算なら「統計的には遍在/特化気味だが、公式がページを立てている概念」を規定分だけ確実に浮上させられる。ページ名の方が見出しより強いシグナルなので加算上限も大きくした（0.25 vs 0.12）。

候補句の切り出しは RAKE 流（ストップワード/句読点区切り、1〜4 語）で品詞タガーを回避。複数形は単数形が語彙にある場合のみ併合。**whats-new/（changelog 転載）ページは語彙抽出から除外**（「Fixed」等の更新動詞が統計を汚染するため。除外前は "fixed" が 73 位に混入→除外で消滅）。カテゴリ素案クラスタは h2 セクションを窓とした NPMI 共起の貪欲平均リンク法（ページ窓では横断語同士がほぼ全共起して 1 塊に潰れるため、窓を狭めた）。

### 3.2 カテゴリ素案クラスタ（上位 60 語・セクション NPMI 共起、v2）

機械出力のまま（ラベルは筆者が括弧で付記）。v1 の 7 クラスタから 19 クラスタへ細分化:

1. **plugin** — marketplace, install（→ プラグイン）
2. **hook** — subagent, skill, output, tool, input, bash（→ 拡張・自動化）
3. **mode** — permission, prompt, config（→ パーミッション・モード）
4. **mcp** — server, mcp server, connect（→ MCP・連携）
5. **settings** — configuration, managed, environment, environment variable, managed settings（→ 設定・管理）
6. **gateway** — organization, cloud, platform, google cloud（→ エンタープライズ基盤）
7. **app** — cli, desktop, terminal（→ アプリ・プラットフォーム）
8. **usage** — response, model, data, error（→ モデル・利用状況）
9. **sdk** — agent（→ Agent SDK）
10. **team** — enterprise, web ／ **command** — directory, worktree ／ **task** — workflow, window, context, action ／ ほか小クラスタ（security, session, control—remote, setup—github 等）

Phase1 で slug から手作業推定した領域（SDK/MCP/エンタープライズ/IDE・プラットフォーム/コア設定…）とほぼ同型の構造が、人手ゼロの統計＋構造シグナルで再現された。

## 4. 考察

**うまくいったこと**
- 作業指示で例示された「環境変数」（見出し横断概念）が上位 1% に入り、**「見出し粒度では取れない横断カテゴリを語の統計で拾う」という狙いを実証**
- **ページ名・見出しの規定加算（v2）が遍在語問題を解消**: 統計だけでは band が殺していた session / command / permission が、公式がページ・見出しを立てている事実を根拠に浮上。「統計の弱点を構造シグナルが補い、構造（見出し粒度が粗い・横断概念が取れない）の弱点を統計が補う」という相補構成になった
- C-value の効果で「mcp server」「managed settings」「permission mode」「context window」等の複合概念語が単語と別に立つ
- クラスタが taxonomy 素案としてそのまま議論の土台になる品質

**限界と対処**
1. **一般語の混入**（output, app, usage, connect, manage 等）: 品詞情報が無いため。ページ名には動詞も含まれる（"Connect to tools" 等）ので v2 の加算がやや助長する面もある。対処: (a) 数十語のドメイン汎用語リスト追加（安価・即効）、(b) 最終確定を人/LLM レビューに置く半自動構成（推奨）
2. **語形のゆれ**（sandbox / sandboxing）: 複数形併合のみの簡易レンマ化では -ing 形のページ名（Sandboxing）を sandbox に集約できない。対処: 派生形の簡易ルール追加（-ing/-tion）か、taxonomy 確定時に人が同義語として束ねる
3. **希少特化語**（slash command, checkpoint）: カテゴリではなくカテゴリ内トピックの粒度。上位語クラスタの「周辺語彙」として NPMI で紐付ければ、分類時のマッチング語彙（同義語表）に活用できる
4. **言語**: 抽出は en 語彙。ja カテゴリ名への写像（environment variable→環境変数）は taxonomy 確定時に一度だけ人手で付ければよい
5. **加算重み（0.25 / 0.12）は暫定値**: 統計コアが [0,1] 程度に正規化されているのに対する経験的な設定。taxonomy レビュー時の体感で調整するノブ

## 5. 運用への組み込み案（Phase3 のたたき台）

```
[不定期・docs大改編時]                          [日次]
llms-full.txt ─→ term_scoring.py ─→ 候補ランキング   サマリ生成(claude -p)
                                      ＋クラスタ素案         │
                                          │                 │ categories.yaml の語彙で
                                    人手レビュー(1回)  ←──── 各変更項目を分類
                                          │                 │
                                    categories.yaml    タグ/グルーピング付きサマリ
                                （カテゴリ名 ja/en＋           │
                                  代表語＋周辺語彙）      チャットルーム通知
```

- **taxonomy 構築**: スコア上位 N ＋クラスタを人がレビューし、8〜12 カテゴリと各カテゴリの語彙（代表語＋NPMI 上位の周辺語）を `categories.yaml` に確定。ここだけ人手（1 回＋大改編時）
- **日次分類**: 変更項目のテキスト・対象 slug を categories.yaml の語彙とマッチング（機械）し、曖昧なもののみ生成時の LLM が判定。Phase1 の B1（インラインタグ）/B2（frontmatter メタ）/A1（グルーピング）のいずれの出力形態にもこの分類結果を流せる
- メンバープロファイル不要。「語彙表のメンテ」も統計スコアの再計算が起点なので、業務の移り変わりはメンバー側がカテゴリを見る目線を変えるだけで吸収できる

## 6. Phase2 で決めたい残論点
