入力: `work/categorize-algorithm/input/作業指示書.md`

## 1. 課題の再定義

現行サマリの分類軸は**「更新の性質」**（新規追加／大幅更新／軽微更新{新機能・機能改善・バグ修正・その他}／新着情報）のみで、**「誰の業務に関係するか」**（機能領域・読者ロール）の軸が存在しない。ハイライト（3〜5件）も全読者共通の編集判断であり、メンバーごとの関心とはずれうる。

したがって解くべき問題は次の2つに分解できる:

- **(P1) 関連性の軸を作る** — 各変更項目に「どの機能領域の話か」を付与する
- **(P2) 読者と軸を対応付ける** — 各メンバーが「自分の領域」を素早く見つけられる形で提示する

## 2. 設計の独立な4軸

どの案も、実際には以下4軸の選択の組み合わせである。Phase2 の協議はこの軸ごとに決めると効率的。

| 軸 | 選択肢 |
|---|---|
| **軸1: カテゴリ体系（taxonomy）の作り方** | (a) 手動固定（8〜10領域を人が定義） / (b) slug 対応表（165ページ→領域の静的マップ） / (c) LLM が毎回動的に抽出 |
| **軸2: 項目→カテゴリの判定方法** | (a) 変更対象ページの slug からの機械マッピング / (b) llms.txt の1行 description の語彙 / (c) 生成時に LLM が判定（changelog 由来のページ無し項目はこれが必須） |
| **軸3: 出力形態** | グルーピング再構成 / インラインタグ / 一覧マトリクス / カテゴリ別ファイル / 構造化データ＋派生ビュー / オンデマンド |
| **軸4: 読者⇔カテゴリの対応付け** | (a) 自己選択（カテゴリ名を見て各自が判断） / (b) ロールプリセット / (c) メンバー個人プロファイル（購読リスト） |

**調査で判明した既存材料**（詳細は調査報告参照）:
- 公式 docs は 165 ページ・フラット構造。明示カテゴリは無いが、slug prefix（`agent-sdk/` 30p、`whats-new/` 17p）と slug 語彙から準カテゴリが構成可能（エンタープライズ/デプロイ、MCP/連携、プラグイン、IDE/プラットフォーム、コア設定、概念/入門、セキュリティ等）
- サマリ生成は SKILL＋テンプレート契約（h2 のみ・`light:*` マーカー・`## N.` 見出しが ja-follow watch の錨）で強く規定されており、**構成変更はテンプレート・derive_light.py・reviewer Agent・watch.py に波及する**
- 各項目は slug（例: `docs/en/permission-modes`）を持つため機械マッピングの土台はある。ただし changelog 由来のページ無し項目には LLM 判定が必要

## 3. 案一覧

### A系 — サマリ本文の再構成（読み方は今のまま、構造を変える）

#### A1. 機能領域別グルーピング
軽微更新（と必要なら大幅更新）の一覧を、現行の性質4分類ではなく**機能領域カテゴリ**（例: SDK / MCP・連携 / エンタープライズ・デプロイ / IDE・プラットフォーム / コア設定・CLI / プラグイン / セキュリティ / その他）でグルーピングする。性質（新機能/改善/修正）は各 bullet 内の接頭ラベルに降格。
- **使い方**: 自分の領域の h2/太字ラベルへ目次ジャンプ → 配下だけ読む
- **長所**: 読者の目的（自分に関係あるか）に直結。単一ファイルのまま。着手待ちタスク②（カテゴリ別グルーピング）と同一方向
- **短所**: 1項目が複数領域にまたがる場合の重複/主従判定が必要。テンプレート・derive_light.py・reviewer 規約の改修が本体
- **実装規模**: 中

#### A2. 冒頭に「影響領域マトリクス」を追加
本文構成は現行のまま、冒頭（概要フェンス直後）に**変更項目×機能領域の一覧表**を1枚追加する。行=変更項目（詳細へのアンカーリンク）、列=領域○付け、または「領域→今回の該当件数＋項目リンク」の索引表。
- **使い方**: 表の自分の列（行）だけ見る → 該当があれば詳細へジャンプ
- **長所**: 既存本文の構造・テンプレート契約を**ほぼ壊さない**（追記のみ）。「有無を素早く確認」という要求に最短
- **短所**: 表が縦に長くなると一覧性が落ちる。項目数が多い日はメンテが煩雑
- **実装規模**: 小〜中

#### A3. ロール別ハイライト
ハイライトを全読者共通の3〜5件ではなく、**ロール別（SDK 開発者向け／管理者向け／CLI 利用者向け…）に各1〜3件**選定するセクション構成に変える。
- **使い方**: 自分のロールのハイライトだけ読む
- **短所**: 「概要=ハイライトと同集合・同数・同順」という現行の厳格ルール（derive_light.py が検証）と衝突し、選定の編集判断も LLM 依存が強くなる（レビューコスト増）
- **実装規模**: 中〜大

### B系 — タグ付け（構造は変えず、項目にメタを埋め込む）

#### B1. インライン領域タグ
全変更項目の bullet 先頭に `[SDK]` `[MCP]` `[Enterprise]` のような**領域タグ**を付ける。構成・順序は現行のまま。
- **使い方**: ブラウザ/エディタの Ctrl+F や grep で自分のタグを検索。「該当タグが無い＝今日は関係なし」が数秒で判る
- **長所**: 実装が最小（生成プロンプト＋タグ語彙表の追加のみ）。既存契約への波及が最小。A1/A2/C系と自由に併用可能
- **短所**: 視認性はグルーピングに劣る。タグ語彙の統制（表記ゆれ）が必要
- **実装規模**: 小

#### B2. frontmatter に領域サマリメタ
ファイル先頭の frontmatter に `影響領域: SDK(3), MCP(1), Enterprise(0)…` のような**件数付き領域リスト**を機械可読で追加。
- **使い方**: ファイルを開いた瞬間（またはツールで）自分の領域の件数が 0 かどうかを確認
- **長所**: 「有無の確認」だけなら最速。通知・配信系（C2/E2）の判定入力としても再利用可
- **短所**: これ単体では「どれが該当か」まで届かない（B1/A 系との併用前提）
- **実装規模**: 小

### C系 — 読者購読モデル（人にマッピングする）

#### C1. メンバープロファイル → 「あなた宛て」セクション
リポジトリに `profiles/<member>.yaml`（購読する slug / prefix / キーワードのリスト）を置き、生成時に各メンバーのプロファイルへマッチした項目を**メンバー別セクション（またはファイル冒頭の宛先一覧）**として出力。
- **使い方**: 自分の名前のところだけ見る
- **長所**: 「自分に関係あるか」の判定を完全に肩代わり。最も要求に忠実
- **短所**: プロファイルの初期作成・継続メンテが必要（メンバーの業務変化に追従）。公開リポジトリにメンバー情報を載せる是非の検討が必要。マッチ漏れ（プロファイルに無い新領域）のリスク
- **実装規模**: 中

#### C2. カテゴリ別派生ファイル／配信
領域カテゴリごとに `latest-<category>.md` を派生生成（derive_light.py の拡張）。さらに進めるなら Mattermost 等のチャンネル別配信に接続。
- **使い方**: 自分の領域のファイル（チャンネル）だけ購読
- **長所**: 読む単位が完全に分離。既存の detail→light 派生機構の自然な延長
- **短所**: ファイル数が増え、アーカイブ・ja-follow watch の対象管理が複雑化。配信まで含めると運用レイヤが増える
- **実装規模**: 中〜大

#### C3. ページ別更新インデックス（逆引き索引）
「日付→変更一覧」ではなく **「ページ(slug)→更新履歴」の逆引き索引** `page-index.md` を累積生成。各 slug 配下に日付と変更1行＋該当サマリへのリンク。
- **使い方**: 自分が業務で使うページ（例: `hooks`, `agent-sdk/python`）の項を見て、新しい日付が増えていないか確認
- **長所**: 「自分の使う機能」を最も直接的な単位（ページ）で表現でき、プロファイル定義が不要。過去に遡った確認にも強い
- **短所**: 日次の「今日なにが起きたか」用途には向かず、latest との併用前提。changelog 由来のページ無し項目の置き場が課題
- **実装規模**: 中

### D系 — 構造化データを正にする（ビューは全部派生）

#### D1. 機械可読 changelog（JSON/YAML）＋派生ビュー
生成パイプラインの一次成果物を**構造化 changelog**（項目ごとに `slug / 領域カテゴリ / 性質分類 / 影響度 / 1行要約 / 詳細アンカー / en・ja リンク`）に変え、latest-detail.md / latest.md / カテゴリビュー / メンバービュー / frontmatter メタを**すべてそこから派生生成**する。
- **使い方**: 読者は好みのビューを読む。ツール（jq / Claude）での問い合わせも可能
- **長所**: A/B/C 系のどの出力形態も後から低コストで追加でき、将来の要件変化に最も強い。タグ語彙・分類の一貫性を機械検証できる
- **短所**: パイプラインの一次成果物の定義変更であり、SKILL・テンプレート・derive_light.py・reviewer・watch.py 全てに波及する最大の改修。ja-follow watch の錨（`## N.` 見出し）互換の維持設計が必要
- **実装規模**: 大

### E系 — オンデマンド（事前分類しない）

#### E1. 問い合わせスキル
サマリ構成は現行のまま、`/check-my-topics permissions hooks sdk` のような**問い合わせ用スキル/スクリプト**を用意し、Claude（または grep スクリプト）が期間内の関連差分の有無を答える。
- **長所**: 生成側の改修ゼロ。任意の切り口に対応
- **短所**: 「開けば分かる」体験にならず、各メンバーがツールを叩く一手間が残る。チーム全員が Claude Code 利用者である前提
- **実装規模**: 小

#### E2. 領域別プッシュ通知
B2 の機械可読メタを入力に、該当領域に変更があった日だけ Mattermost 等へ領域別に通知を出す（サマリ本文は現行のまま）。
- **長所**: 「見に行く」から「来たら見る」へ転換。0件の日は何も来ない＝確認コストゼロ
- **短所**: 配信基盤・チャンネル設計という別レイヤの構築が必要。リポジトリ外の運用が増える
- **実装規模**: 中〜大（配信基盤次第）

## 5. 組み合わせの推奨候補（Phase2 のたたき台）

案は排他ではなく積層できる。段階導入の観点で:

1. **第1候補（本命・段階導入）**: **B1＋B2 → A1** — まずタグと frontmatter メタで最小コストに「有無確認」を成立させ、タグ語彙（=taxonomy）が安定したら A1 のグルーピング再構成へ昇格する。taxonomy は軸1-(a)手動固定（8前後）＋軸2-(a) slug 対応表＋changelog 由来のみ LLM 判定、が最も検証しやすい
2. **第2候補（最小変更で完結）**: **A2 単独** — 冒頭マトリクス追記のみ。既存契約をほぼ壊さないが、taxonomy 整備は結局必要
3. **第3候補（要求に最忠実）**: **C1（＋B2）** — メンバープロファイル駆動。「メンバー情報を公開リポジトリに置けるか」「プロファイル保守を誰がやるか」が論点
4. **長期投資**: **D1** — 今後もビュー要件が増えるならどこかで踏む価値がある。第1候補の taxonomy/タグはそのまま D1 の入力設計に転用可能

## 6. Phase2 で決めたい論点

1. taxonomy は手動固定か動的か（推奨: 手動固定 8前後＋slug 対応表。当リポジトリの着手待ちタスク②の論点と同一）
2. 適用範囲: latest-detail のみか、latest（ライト版）・mcp サイト・archives 遡及も含むか
3. 読者対応付けの深さ: カテゴリ自己選択で足りるか、メンバープロファイル（C1）まで踏み込むか（メンバー情報の公開可否を含む）
4. 複数領域にまたがる項目の扱い（主領域1つに寄せる／複数タグ許容）
5. 既存契約（テンプレート・derive_light.py・reviewer・ja-follow watch の錨）への波及をどこまで許容するか
6. 出力先はリポジトリ内ファイル完結か、配信（E2）まで視野に入れるか
